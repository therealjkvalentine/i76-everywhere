## Contract

Redraft (requeue reason: G4 name disagreement, first-round names zfs_CreateArchive / zfs_CreateFile). What the
function creates, from the evidence: it opens `path` for writing (fopen at 0x4b9645; the first fopen at
0x4b960c is only an existence probe that yields 'File "%s" already exists' and return 0) and writes two blocks:
a 0x1c-byte header whose bytes are 'Z','F','S','F' (0x5a 0x46 0x53 0x46) followed by the dwords 1, 0x10, 100,
0, param_2, 0x1c, then a zeroed 0xe14-byte (901-dword) block. That header and that 0xe14 block are exactly
what zfs_Open (0x4b9800, supported, zfs) validates ('Z','F','S','F', 1, 0x10, 100, else 'Invalid header in
file "%s"') and reads back with fread(...,0xe14,1,...) as a dtable. The sole caller 0x4b9740 calls this with
param_2 = 0 when its own fopen fails with errno 2 and then passes the re-opened FILE* to zfs_Open. So the thing
created is a ZFS archive (header plus one empty directory table); the on-disk file is only its container. Hence
the words CreateArchive: "File" in a zfs_ name would collide with the archive's own entries (zfs_ReadRecord
0x4b9bd0 reads those), and the three strings' word "file" is the generic noun for the container, not the
subject. Returns 1 on success, 0 on every failure after sprintf into the bss buffer 0x5db998.

## Hypotheses

- hypothesis: The 0x1c-byte header is the ZFS archive header: magic 'ZFSF' at +0, version 1 at +4, 0x10 at +8, 100 (entries per directory table) at +0xc, 0 (entry count) at +0x10, param_2 at +0x14 (zfs_Open stores it at archive+0x1c), 0x1c (first dtable offset) at +0x18; the 0xe14 block is one empty directory table (4-byte next-offset plus 100 x 0x24-byte entries = 0xe14, matching zfs_Open's loop of 100 entries of 0x24 bytes).
