# Geomorphing variants and what each needs from the renderer

Scope: the seven well-known forms of terrain geomorphing (Röttger 1998, Hoppe 1998, de Boer 2000 / Wagner 2003, Ulrich 2002, Strugar 2009, Losasso & Hoppe 2004, and the "blend the new midpoint from the parent edge" form), assessed against a 1997 software / fixed-function renderer whose quadtree is rebuilt every frame from the camera with no state kept between frames, whose split distance per tile is known at the moment the split is decided, whose midpoint vertices are written by an edge-split routine, whose shading is per-vertex Gouraud from vertex normals, and whose transform / clip / draw path can only be hooked. The Interstate '76 facts below are taken from the brief and are not independently verified here; nothing about the I'76 engine is asserted beyond them.

Source-access notes for the report writer: the primary PDFs were downloaded and text-extracted locally (Röttger, de Boer, Strugar, Losasso & Hoppe, Hoppe 1998, Wagner). Thatcher Ulrich's SIGGRAPH 2002 course-notes PDF (tulrich.com/geekstuff/sig-notes.pdf) has no usable text layer; his SIGGRAPH 2002 slide text pages were used instead. Greek symbols were lost in several extractions; where a formula is quoted the symbols were reconstructed from the surrounding prose and are flagged.

## Key question 1: per-variant requirements (per-vertex data, parent height at creation, cross-frame state, morph-factor source, cost)

### Takeaway
Every variant except Hoppe 1998 computes the morph factor as a pure function of the camera's current distance (or grid position) and the tile's own split / LOD range, so none of them needs state across frames; Röttger 1998 is literally the "blend the new midpoint vertex from the parent-edge average toward its true height, with b = 2(1 - f) clamped to [0,1], where f is the same ratio used to decide the split" form, evaluated top-down on a quadtree rebuilt each frame.

### Cited Findings

**Röttger et al. 1998 (quadtree, rebuilt each frame, CPU)**
- Subdivision criterion without roughness: "l / d < C ... for some constant C, where l is the distance to the eye point, and d is the edge length of the block ... C is a configurable quality parameter. The constant C controls the minimum global resolution. As C increases, the total number of vertices per frame grows quadratically." Distances use the L1 norm "for performance". — [Röttger 1998, §2.2](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Revised criterion with roughness: "f = l / (d · C · max(c · d2, 1)) ... subdivide if f < 1" (equation 3); "d2 = (1/d) · max_{i=1..6} |dh_i|" (equation 2) where the six dh_i are the elevation differences along the node's four edges and two diagonals; "the d2-value times d is an upper bound for the error introduced by dropping one level of detail". The constant c "specifies the desired global resolution ... by adjusting c to the current system load, a constant frame rate can be maintained." — [Röttger 1998, §2.2](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Blend factor: "Since morphing only happens in the leaf nodes of the current triangulation, we can use b = 2(1 - f) clamped to the range [0,1] as a blending factor to morph between two levels of detail ... there are up to five vertices where morphing might have to be performed for each quadtree node ... The elevation at these points is interpolated linearly with factor b between the elevation of the lower level (which is the average of the two corresponding corner points) and the elevation of the higher level. The latter is taken directly from height field data." — [Röttger 1998, §2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Per-vertex data: the decision variable f itself is the only input; the "parent height" is the average of the two edge endpoints, i.e. no stored data beyond the heightfield. The blend values are stored in the quadtree matrix as bytes: "we store blending factors in the matrix, rather than boolean values ... We avoid storing floating point values by using one byte per entry. As a result, we have 255 morphing steps, which is precise enough in practice." — [Röttger 1998, §2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Cost / parameters: "the condition is evaluated only once for a complete triangle fan, which consists of up to 10 vertices"; results on an SGI Maximum Impact (250 MHz R4400) "maintaining a constant frame rate of 25 Hertz"; "The quality control C was set to a value of 8, which also proved to be a good choice for other data sets. The value of c was dynamically chosen as to maintain a fixed frame rate of 25 Hertz, which resulted in approximately 1600 triangles" per frame (the sentence truncates in the extraction). The abstract claims the geomorph "operates top down on the quadtree ... at virtually no additional cost". — [Röttger 1998, §2.2, §3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)

**Hoppe 1998 (view-dependent progressive mesh, time-based geomorphs, CPU)**
- Morph is time-based, not distance-based: "When the refinement criteria indicate the need for an ecol or vsplit, instead of performing the transformation instantaneously, we perform it as a geomorph by gradually changing the vertex geometry over several frames." The new vertex starts at its sibling's geometry: "we initially assign the new vertex vu the same geometry as its sibling vt, and only gradually modify the geometry of vu to its refined state over the next gtime frames. The parameter gtime is user-specified; in our prototype we have set it equal to the frame rate (30-72), so that geomorphs have a lifetime of one second." — [Hoppe 1998, §4.2](https://hhoppe.com/svdlod.pdf)
- Per-vertex state across frames: a VertexMorph record with "bool coarsening", "short gtime // # of geomorph frames remaining", "VGeom vg_refined // refined geometry (back-up copy)" and a per-frame increment "vm.vginc = (vm.vg_refined - vu.avertex.vgeom) / gtime"; each frame "for each morphing vertex, we advance its geometry and decrement its gtime field. When gtime reaches 0 ... the VertexMorph record is deleted." — [Hoppe 1998, §4.2](https://hhoppe.com/svdlod.pdf)
- Needs the view extrapolated: "anticipate the viewer location gtime frames into the future when evaluating the screen-space error metric ... by extrapolation based on the current per-frame viewer velocity". — [Hoppe 1998, §4.2](https://hhoppe.com/svdlod.pdf)
- Cost: a 710x520 flythrough at "a constant frame rate of 30 frames/sec" with "approximately 12,000 active faces", amortizing adapt_refinement over 3 frames; "number of morphing vertices g = 1,500". — [Hoppe 1998, §6](https://hhoppe.com/svdlod.pdf)

**de Boer 2000 geomipmapping (per-chunk LOD, CPU-side "trilinear" morph)**
- Level selection: "D_n = |delta| · C" (Equation 1), "C = A / T" (1a), "A = n / |t|" (1b, n the near plane, t the top coordinate of the near plane), "T = 2·tau / vres" (1c, vres the vertical resolution in pixels, tau the max screen-space pixel error); delta is the max height change caused by removing a level's vertices. The squared form "D_n^2 = delta^2 · C^2" (Equation 2) saves the square root. Demo used "tau = 8.0" at "an average frame-rate of 50 s^-1 ... with about 11,000 triangles per frame, on a PentiumII 434 Mhz with a Diamond Viper 550". — [de Boer 2000, §2.3.1, §4](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Morph factor: "t = (d - D_n) / (D_{n+1} - D_n)" (Equation 3); "v' = v - t · delta_v" (Equation 4), "delta_v is the height change (geometric error) of v", applied to the "white" (odd) vertices of the current level. "This will slowly 'morph' level 0's geometry to level 1's until d has reached D_1, after which level 0 can be replaced by level 1." — [de Boer 2000, §3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Per-vertex data: delta_v per odd vertex (precomputed per level); the morph factor is per chunk. No cross-frame state. — [de Boer 2000, §3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Author's own position: tau "set to 1 or less will eliminate popping altogether" at a high triangle cost; the trilinear morph lets tau be raised while popping is "totally eliminated". — [de Boer 2000, §3.1, §5](https://www.flipcode.com/archives/article_geomipmaps.pdf)

**Wagner 2003 (de Boer-style patches, morph in the vertex shader)**
- The tessellation routine "returns a tessellation factor in form of a floating point value where the integer part means the current level and the fractional part denotes the tweening factor. E.g. a factor of 2.46 means that tweening is done between levels 2 and 3 and the tweening factor is 0.46." Only odd-indexed vertices move; each moves "into the middle position" between its two surviving neighbours (three cases A/B/C). — [Wagner 2003, pp. 5, 7](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)
- Final position in the shader: "PosFinal = PosBase + tweeningI*dI + tweeningL*dL + tweeningR*dR + tweeningT*dT + ..." with nine factors per patch (self, four neighbours, four "inner neighbour" factors tweeningA = (1.0 - tweeningL) * tweeningI); "nine multiplications and nine additions just for the geomorphing task ... quite slow in terms of performance doing it on the CPU". — [Wagner 2003, p. 8](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)
- Measured cost (Athlon 1300 + GeForce3): Static LOD 504 fps / Software (CPU) morphing 312 fps / Hardware morphing 501 fps on the minimum scene; 231 / 205 / 230 on the full scene; "software morphing needs to send all vertices over the bus each frame". — [Wagner 2003, Table 1](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)

**Ulrich 2002 chunked LOD (per-chunk morph parameter, precomputed meshes)**
- Error metric: "rho = K * delta(chunk) / D(viewpoint, chunk)" with K = W / (2 * tan(FOV/2)) (W viewport width), rho the on-screen pixel error, delta(chunk) the chunk's max geometric error, tau the allowed pixel error. — [Ulrich SIGGRAPH 2002 slide "chunklod math"](https://tulrich.com/geekstuff/siggraph02-slides/text16.html)
- Morph: "Each vertex in a chunk's mesh is matched to an approximate position on its parent chunk. A single blend parameter, f, interpolates the whole chunk: at f = 0 vertices sit at the parent's approximation, and at f = 1 they reach their exact positions. The parameter is driven by LOD. A node splits when f hits 0, and its children start at f = 1, so the transition is seamless." (paraphrase by the fetch tool of slide "morph"). — [Ulrich SIGGRAPH 2002 slide "morph"](https://tulrich.com/geekstuff/siggraph02-slides/text26.html)
- The chunk data carries the morph deltas: "Chunking does some decimation, adds mesh and morph info == 327 MB w/ 4-meter error" for the 512 MB Puget Sound height set; runs "~30+ fps on my half-decent laptop". — [Ulrich SIGGRAPH 2002 slide "puget stats"](https://tulrich.com/geekstuff/siggraph02-slides/text23.html)
- Ulrich's project page: the renderer does "CLOD, with geomorphs, using batched primitives"; a 2004 extension did "vertex-morphing using a Cg vertex program"; the demo used "around 2-pixel screen-space error tolerance" with geometry preprocessed at "a 4 meter error tolerance". — [tulrich.com chunklod page](https://tulrich.com/geekstuff/chunklod.html)
- Strugar's characterisation: in "[Ulrich 02] ... the morph is performed per-node (per-chunk)", vs CDLOD where "each vertex is morphed individually based on its own LOD metric". — [Strugar 2009, "Morph implementation"](https://github.com/fstrugar/CDLOD)

**Strugar 2009 CDLOD (per-vertex morph on a quadtree, vertex shader)**
- LOD ranges: "the range of each level being two times larger than that of the previous one, and the range of the final level (largest, least detailed) representing the required total viewing distance"; the factor two follows from "the complexity difference between each successive LOD level is fixed to four". — [Strugar 2009, "LOD distances and morph areas"](https://github.com/fstrugar/CDLOD)
- Morph area: "the morph area is also defined, marking the range along which a higher complexity mesh will morph into the lower one. This morph area usually covers the last 15%-30% of every LOD range." — [Strugar 2009](https://github.com/fstrugar/CDLOD)
- Per-vertex factor: "the approximate distance between the observer and the vertex is calculated to determine the amount of morph required ... morphK ... ranging between 0 (no morph, high detail mesh) and 1 (full morph, four times fewer triangles), is used to gradually move each morph mesh vertex towards the corresponding no-morph one. A morph vertex is defined as a grid vertex having one or both of its grid indices (i, j) as an odd number, and its corresponding no-morph neighbour is the one with coordinates (i - i/2, j - j/2)" [sic; the odd index snapped to the even neighbour]. HLSL: "float2 fracPart = frac( gridPos.xy * g_gridDim.xy * 0.5 ) * 2.0 / g_gridDim.xy; return vertex.xy - fracPart * g_quadScale.xy * morphK;" then "the z-component is obtained by sampling the heightmap with texture coordinates calculated from x and y components using a bilinear filter (filtering is only needed for vertices in the morph region)". — [Strugar 2009, "Morph implementation"](https://github.com/fstrugar/CDLOD)
- Per-vertex data: none beyond the grid index; the coarse height is obtained by moving the vertex in XY onto the parent edge and re-sampling the heightmap. No cross-frame state. Requires "Shader Model 3.0 and above" for the vertex-shader heightmap fetch. — [Strugar 2009, abstract and "Performance on older hardware"](https://github.com/fstrugar/CDLOD)
- Pre-shader-model-3 fallback: "merging the CDLOD and ChunkedLOD [Ulrich 02] techniques ... Each vertex can contain additional morph data so that during the LOD transition some vertices can be moved into neighbouring ones in the vertex shader, eliminating triangles and effectively morphing the more detailed LOD mesh into the less detailed one." — [Strugar 2009, "Performance on older hardware"](https://github.com/fstrugar/CDLOD)

**Losasso & Hoppe 2004 geometry clipmaps (nested regular grids, vertex shader)**
- Per-vertex data: "each vertex stores (x, y, z, z_c), where z_c is the terrain height in the next-coarser level l-1"; morphed elevation "z' = (1 - alpha) z + alpha z_c" (symbols reconstructed; extraction lost the Greek). — [Losasso & Hoppe 2004, §6.2](https://hhoppe.com/geomclipmap.pdf)
- Blend parameter is spatial, not temporal: "alpha = max(alpha_x, alpha_y)" with alpha_x = clamp(( |x - v_x| - ((x_max - x_min)/2 - w - 1) ) / w, 0, 1) and similarly for y, where v_x, v_y are "the continuous coordinates of the viewpoint in the grid of clip_region(l), and x_min, x_max the integer extents of active_region(l). The desired property is that alpha evaluates to 0 except in the transition region where it ramps up linearly to reach 1 at the outer perimeter. These evaluations are performed in the GPU vertex shader using about 10 instructions". "Thus the transition is not time-based but instead tracks the continuous viewer position." — [Losasso & Hoppe 2004, §6.2](https://hhoppe.com/geomclipmap.pdf)
- Transition width: "Through experimentation, we have found that a transition width w of n/10 grid units works well. If w is much smaller, the level boundaries become apparent. And if w is much larger, fine detail is lost unnecessarily." Constraint (4): "the render region must be at least two grid units wide to allow a continuous transition between levels." — [Losasso & Hoppe 2004, §5-6](https://hhoppe.com/geomclipmap.pdf)
- No cross-frame state for the morph itself (the clipmap data is incrementally updated, but alpha is recomputed from position each frame). — [Losasso & Hoppe 2004, §6.2](https://hhoppe.com/geomclipmap.pdf)

### Inferences
- The brief's "simple form" (blend the new midpoint from the parent edge's interpolated height to its true height over a band inside the split distance) is Röttger 1998's scheme exactly: parent height = mean of the two edge endpoints, factor b = 2(1 - f) where f is the split ratio, applied to the (up to five) midpoint vertices a split creates. Because f is recomputed from the camera every frame and nothing else is stored, it is the only published variant whose state model matches "quadtree rebuilt every frame, no state kept".
- For a renderer whose edge-split routine already interpolates along the parent edge to place the midpoint, the parent height is in hand at creation time (the endpoint heights are the operands); the only extra per-vertex work is one lerp between that interpolated value and the true height. (Inference from Röttger's definition of the lower-level elevation as the corner average plus the brief's description of the edge-split routine; whether I'76's routine actually reads both endpoints was not verified.)
- de Boer's t = (d - D_n)/(D_{n+1} - D_n) and Röttger's b = 2(1 - f) are the same quantity expressed differently: both are the normalised position of the camera inside the band between "this level's split distance" and "the next level's split distance"; with Röttger's constant C and a 2x size ratio between levels, b runs 0 -> 1 as l/d goes from C down to C/2, i.e. across the entire half-range between consecutive splits, not a 15-30 % tail as in CDLOD.
- The time-based form (Hoppe 1998) is the only one that requires a per-vertex record surviving across frames (gtime, increment, backup geometry) and a velocity extrapolation; it is the worst fit for a stateless per-frame rebuild and is only worth it when the LOD decision itself is not a smooth function of distance (progressive meshes).
- Cost ordering (CPU-side, per frame): Röttger / simple form = one lerp per morphing midpoint vertex plus one scalar f per node that is already being computed for the split decision; de Boer = one multiply-add per odd vertex plus one t per chunk; Ulrich = one per-chunk f plus a multiply-add per vertex over precomputed deltas; CDLOD = an XY snap plus a height re-fetch per odd vertex; Hoppe = a per-vertex add per frame plus bookkeeping. Wagner's measurement (312 vs 504 fps) shows CPU-side morphing on 2003 hardware was dominated by re-uploading vertices, a cost that does not exist when the CPU already writes the full vertex stream each frame (as the brief says I'76 does).

### Gaps
- Ulrich's SIGGRAPH course-notes PDF could not be text-extracted (no text layer), so the exact formula he uses to derive the per-chunk morph parameter from rho / tau (commonly quoted as f = clamp((tau_max_or_ratio - rho)/..., 0, 1)) could not be confirmed from the primary source; only the slide-level description (f from LOD, 0 at split, children at 1) is cited.
- Strugar's source (CDLODQuadTree.cpp) could not be fetched (raw.githubusercontent returned 404 / 403), so the exact per-level morph-start ratio constants in his demo settings are not confirmed; only the paper's "last 15 %-30 %" statement is.

## Key question 2: CDLOD's morph area, consistency across levels, and picking the band width

### Takeaway
CDLOD's morph band is the outer 15-30 % of each level's range, the ranges double per level so the bands nest, and the morph is seam-free only because the vertex distance and the coarse height are computed by functions that give identical results on both sides of every node edge; the band must be wide enough that a vertex's per-frame height change projects to under a pixel at the fastest camera speed, which can be derived from Ulrich's K factor.

### Cited Findings
- CDLOD morph area: "This morph area usually covers the last 15%-30% of every LOD range." LOD ranges: each "two times larger than that of the previous one". — [Strugar 2009](https://github.com/fstrugar/CDLOD)
- Why consistency across nodes/levels is required: "The vertex position used to calculate this distance can be an approximation as long as the approximating function is consistent over the whole dataset domain. This is necessary since, in order to prevent seams, the vertices on the node's grid mesh edges must remain exactly the same as the ones on the neighbouring nodes. In our case, x (latitude) and y (longitude) components will always be correct as the same function is used to stretch them to the world space, but z (height) must either be approximated or sampled from the heightmap using a consistent filter." — [Strugar 2009, "Morph implementation"](https://github.com/fstrugar/CDLOD)
- Granularity constraint: "a single quadtree node can only support transition between two LOD layers. This limits the minimum possible viewing range, or the minimum quadtree depth, because only one smooth transition can be performed between two LOD layers over the area of the same node ... The size of the morph area can also be decreased to mitigate this problem, but that can make the transition between levels noticeable." Debug builds "detect a possibility of such a situation and display a warning". — [Strugar 2009, "Granularity issues"](https://github.com/fstrugar/CDLOD)
- Ranges computed to give "approximately the same average number of triangles per square unit of screen over the whole rendered terrain". — [Strugar 2009](https://github.com/fstrugar/CDLOD)
- Clipmaps band width: "a transition width w of n/10 grid units works well. If w is much smaller, the level boundaries become apparent." — [Losasso & Hoppe 2004, §6.2](https://hhoppe.com/geomclipmap.pdf)
- Röttger's band: b = 2(1 - f) clamped, so the morph spans f in [0.5, 1], i.e. the whole half-range from the split distance down to half of it; restricted by "the level difference of adjacent blocks is less than or equal to one". — [Röttger 1998, §2.2-2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Per-pixel projection factor: "rho = K * delta(chunk) / D(viewpoint, chunk)", "K = W / (2 * tan(FOV/2))". — [Ulrich SIGGRAPH 2002 slide "chunklod math"](https://tulrich.com/geekstuff/siggraph02-slides/text16.html)
- A GameDev.net implementer's note on the simple distance-ramp form: the morph amount ran "from 0.0 at the finest level to 1.0 at the coarsest. They changed it to a linear blend between 0.0 and 2.0 and clamped the resulting amount to 1.0 to avoid visible popping when a patch splits." (search-result paraphrase; the page itself returned 403). — [GameDev.net blog "Vertex morphing action"](https://gamedev.net/blogs/entry/1007337-vertex-morphing-action)
- Unigine's docs on tuning: "if LOD distances are set too small, the LODs follow each other too closely and geomorphing becomes more obvious" (search-result paraphrase). — [Unigine terrain optimization docs](https://developer.unigine.com/en/docs/2.2/objects/objects/terrain/terrain_optimization/?rlang=cpp)

### Inferences
- Mapping to a split-at-12.9x-size rule (from the brief): a tile of size s splits at D_split = 12.9 s (always) or 18.3 s (steep). The morph band in Röttger's form would be [D_split/2, D_split] (b = 2(1 - l/(C d)) is 0 at l = C d and 1 at l = C d / 2); a CDLOD-style band would be [D_split, (1 + beta) D_split] measured from the parent's perspective, with beta = 0.15-0.30 of the parent's range (which is 2 D_split for the parent). Which end of the band is "fully morphed" is a convention; both references put b = 0 (child vertices sitting on the parent edge, i.e. the parent mesh) at the moment the split decision flips, so the split itself moves nothing.
- Ring positions must be consistent across levels because a vertex on the shared edge of two sibling tiles is morphed by both tiles; if the two compute different factors (different distance approximations, different "parent" heights) the shared vertex gets two heights and a crack opens. In a quadtree rebuilt from one camera with one distance rule, an edge midpoint's factor is identical from both sides provided it is computed from the midpoint's own position (or from the parent edge, which both children share), not from each child's centre. (This is what Strugar's "consistent function" sentence means; applying it to a per-node rather than per-vertex factor is inference.)
- Band width for an invisible morph (inference, derived from Ulrich's K): a morphing midpoint moves in height by delta_h · (db/dt). With b linear across a band of world-length B and the camera closing at speed v, db/dt = v / B, so the per-frame height change is delta_h · v · dt / B, which projects to about K · delta_h · v · dt / (B · D) pixels at distance D. Requiring < 1 px per frame at the split distance D = D_split gives B > K · delta_h · v · dt / D_split. With Röttger's band B = D_split/2 = 6.45 s this becomes delta_h < 6.45 s · D_split / (K · v · dt) = 6.45 · 12.9 s^2 / (K · v · dt). Numbers for s, delta_h, v, W, FOV and dt have to come from the I'76 measurements (not invented here); the structure says the simple half-range band is far wider than CDLOD's 15-30 % tail, so it is the more forgiving choice for a first retrofit, at the cost that a larger share of visible tiles is in a partially morphed (slightly flattened) state.
- A narrower band concentrates the motion into fewer frames; Strugar warns the transition becomes "noticeable" if the morph area is shrunk, and Losasso & Hoppe say boundaries "become apparent" if w is much smaller than n/10 — both are consistent with the per-frame-pixel-motion criterion above.

### Gaps
- Neither Strugar nor Losasso & Hoppe give a quantitative "sub-pixel per frame" derivation; the formula above is inference from the chunked-LOD pixel-error metric.
- Strugar's demo configuration files (the concrete morph-start ratios per dataset, reportedly in the 0.66-0.85 range in community reimplementations) could not be fetched; the brief's "0.7-0.85" figures could not be sourced to a primary document and are left uncited.

## Key question 3: T-junctions and cracks between a morphed tile and an unmorphed neighbour

### Takeaway
Three families of fix exist: constrain the tree so neighbours differ by at most one level and give shared-edge vertices one agreed factor (Röttger, de Boer's "omit the edge vertex", Wagner's finer-follows-coarser); hide the gap with a vertical skirt per chunk (Ulrich) or zero-area stitching triangles (clipmaps); or design the morph so that the fully-morphed fine mesh is geometrically identical to the coarse mesh and every edge vertex is morphed by a function both sides compute identically (CDLOD). A restricted quadtree rebuilt each frame already gives the first family's precondition for free; the remaining obligation is only that a shared midpoint's blend value is the same from both sides.

### Cited Findings
- Röttger: adjacency is restricted by propagating d2 bottom-up so that "the level difference of adjacent blocks is less than or equal to one. Since the surface roughness of adjacent blocks may differ significantly, this is necessary to build a conforming mesh without holes." Condition (4): "f1 < f2 <=> d1·l1/d2_1 < d2·l2/d2_2"; the propagated d2 "of each block is the maximum of the local value and K times the previously calculated values of adjacent blocks at the next lower level", "K = C / (2(C - 1))" for C > 2. Crack avoidance under morphing: "Blending factors of adjacent blocks differ slightly due to a variation of the distances to the point of view. Thus, the interpolated elevation at the midpoint of a shared edge is different for adjacent blocks, causing cracks to appear. In order to avoid this, we store blending factors in the matrix, rather than boolean values. The blending value for a shared edge is obtained by taking the minimum of the blending values of the two involved blocks." — [Röttger 1998, §2.2-2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Röttger's mesh is triangle fans of "up to 10 vertices" per node, with a fan vertex omitted when "the neighboring node" is not subdivided, i.e. the fan adapts to the coarser neighbour. — [Röttger 1998, §2.1](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- de Boer: adding vertices to the coarser neighbour "is a slow and memory consuming task, and so this method should be avoided"; levelling the finer edge's vertices "will cause so called T-junctions, or T-vertices. Because of floating-point inaccuracies, these will deliver a very noticable 'missing pixels' effect"; his fix: "By omitting these vertices from being 'connected', the edge will seamlessly fit with the lower detail GeoMipMap. A fast way of rendering this is by using two triangle-fans for this edge ... Omitting rather than adding vertices, has the advantage of not having to change anything for any GeoMipMap ... the only thing that changes is the connection data." And for morphing: "Any edge's white vertices that are neighbours with lower detail GeoMipMaps should not be multiplied by t, as these do not contribute to the GeoMipMap anymore." — [de Boer 2000, §2.3.2, §3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Wagner: T-vertices "will not be exactly on the edge of the neighboring triangle and small gaps only a few pixels in size can become visible. Even worse, when moving the camera these gaps can emerge and disappear every frame"; fix is "a border of 'adapting triangles'" on the finer patch, and under morphing "it is necessary that the finer patch allows the coarser one to dictate the border vertices' position", requiring the extra neighbour factors and tweeningA = (1.0 - tweeningL) * tweeningI for the vertices one row in from the border. — [Wagner 2003, pp. 4, 7-8](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)
- Ulrich: "No perfect answers; lots of different hacks"; "Flanges, zipper/ribbon meshes"; chosen fix: "a conservative, static skirt mesh around its outside edge. The skirt is fully vertical, so it doesn't interfere with neighboring chunks. Because the chunk knows its edge geometry, the skirt can be safe without being overly conservative. Texture stretch from the skirt is essentially invisible at the tessellation levels used." (fetch-tool paraphrase of the slides). — [Ulrich slides "cracks"](https://tulrich.com/geekstuff/siggraph02-slides/text28.html), [Ulrich slides "cracks2"](https://tulrich.com/geekstuff/siggraph02-slides/text29.html)
- Losasso & Hoppe: the transition morph closes the gaps but "the T-junctions along the boundaries still result in dropped pixels during rasterization. To stitch adjacent levels into a watertight mesh, we use the simple solution of rendering zero-area triangles along the render region boundaries"; constraint (3): "the perimeter of active_region(l) must lie on 'even' vertices, to enable a watertight boundary with coarser level l-1." — [Losasso & Hoppe 2004, §5, §6.2](https://hhoppe.com/geomclipmap.pdf)
- Strugar: the morph reduces "every block of eight triangles from the more detailed mesh ... into the corresponding block of two triangles on the less detailed mesh by gradual enlargement of the two triangles and reduction of the remaining six triangles into degenerate triangles that are not rasterized. This process produces smooth transitions with no seams or T-junctions"; "When all vertices of a node are morphed to this low-detail state, the mesh then effectively contains four times fewer triangles and exactly matches the one from the lower LOD layer; hence it can be seamlessly replaced by it." He criticises stitching strips: "besides adding to the rendering cost, can cause various issues such as artifacts when rendering shadow maps; unwanted overdraw when the terrain is rendered transparently". — [Strugar 2009](https://github.com/fstrugar/CDLOD)

### Inferences
- What a per-frame restricted quadtree gives for free: the neighbour-level-difference <= 1 constraint (Röttger's precondition), and, if the fans / triangles along a coarse neighbour already drop the midpoint (as Röttger's fan and de Boer's omitted edge vertex do), the geometric crack is already closed in the unmorphed renderer. Morphing adds exactly one new obligation: a midpoint on an edge shared by two subdivided tiles must receive one blend value. Röttger's rule "min of the two blocks' values" is the published answer; with a per-node hash already keyed by corner and size (per the brief), storing one byte per node and taking the min across the shared edge is a direct transliteration of his byte matrix, and it needs no cross-frame state because the matrix is refilled each frame.
- A midpoint on an edge whose neighbour is NOT subdivided is not drawn by the neighbour at all (restricted quadtree), so whatever height the subdivided side gives it, the shared edge is a straight line on the coarse side and a two-segment line on the fine side; the morph only changes how far the fine side's midpoint deviates from that line, so no new crack is created and at b = 0 the two sides coincide exactly. This is why de Boer says such vertices "should not be multiplied by t": they must be pinned to the coarse edge (b = 0), which is the fully-morphed position, not the true height.
- Skirts (Ulrich) are the cheapest fix only if the renderer can take extra triangles per chunk and tolerate texture stretch; against a hard 32,767-vertex-per-frame budget (from the brief) they spend vertex indices on invisible geometry, so they are a poor fit. Zero-area stitching (clipmaps) likewise costs indices. The restricted-quadtree + agreed-midpoint route spends none.

### Gaps
- Whether I'76's existing per-frame fan / strip generation already omits midpoints against coarser neighbours (de Boer's rule) was not verified here; the brief says the quadtree is restricted but not how the edges are triangulated.

## Key question 4: morphing the shading (normals, Gouraud colours)

### Takeaway
None of Röttger, de Boer, Ulrich or Strugar morphs vertex normals or Gouraud colours: Röttger does not discuss it, de Boer notes a "slight change in (gouraud) shading" when connectivity changes and leaves it, Wagner (de Boer's shader-era successor) declares vertex normals unusable under LOD and switches to a lightmap, Strugar and Losasso & Hoppe move shading off the vertices entirely (normal maps), and only Hoppe 1998 interpolates normals (over the unit sphere) and colours alongside positions during the geomorph.

### Cited Findings
- de Boer: "A downside of this method is that, when changing connectivity of vertices, a slight change in (gouraud) shading will occur. This sometimes can be spotted in real-time, but it is only slightly noticable." — [de Boer 2000, §2.3.2](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Wagner: "Because of the dynamic nature of the triangulation, vertex normals cannot be used for lighting. Instead a pre-calculated lightmap is used." "Applying dynamic light by using surface normals would be the easiest way to go, but would result in strange effects when patches switched tessellation levels. The reduction of vertices goes hand in hand with the loss of equal number of normals. When a normal is removed the resulting diffuse color value is removed too. The user notices such changes very easily - especially if the removed normal produced a color value which was very different from its neighboring color values ... we can use a pre-calculated lightmap which is by its nature more resistant to vertex removal than per-vertex lighting." — [Wagner 2003, abstract and p. 4](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)
- Hoppe 1998: "Besides position, other vertex attributes interpolated during a geomorph may include normal, color, and texture coordinates. Most attributes are linearly interpolated. Normals are interpolated over the unit sphere." — [Hoppe 1998, §4.2](https://hhoppe.com/svdlod.pdf)
- Strugar: swapping between meshes "of different triangle count and shape ... differences in vertex output interpolation will result in 'popping' artifacts that appear if any vertex-based effect (such as vertex lighting) is used"; CDLOD "inherently avoids these problems because the algorithm used to transition between LOD levels completely transforms the mesh of a higher level into the lower"; his demos light "based on one directional light and normals from the high resolution normalmap texture" (califmtns, hawaii) or "an overlay texture with baked lighting" (puget). — [Strugar 2009, §2 and "Results"](https://github.com/fstrugar/CDLOD)
- Losasso & Hoppe: shading uses a normal map, and texture LOD is blended with the same alpha as the geometry: "When rendering level l, we provide the shader with the textures from levels l and l-1, and blend these using the same alpha parameter already computed in the vertex shader for geometry transitions." Without that, texture-resolution boundaries "are visible during viewer motion as 'advancing fronts' over the terrain surface." — [Losasso & Hoppe 2004, §6.3](https://hhoppe.com/geomclipmap.pdf)
- Röttger's paper discusses "lighting artifacts for non-silhouette polygons" only as an argument against silhouette-based criteria; the geomorph section specifies the blended quantity as elevation only. — [Röttger 1998, §1, §2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)

### Inferences
- For a Gouraud renderer the vertex colour is a function of the vertex normal, and the normal of a midpoint vertex on a flat parent edge equals (or is close to) the interpolated normal of the endpoints only if the normal is computed from the morphed geometry; if the renderer takes normals from a precomputed per-vertex table (true-height normals), a newly split midpoint at b = 0 sits on the parent edge but is lit with its true-surface normal, which is exactly the "removed normal produced a colour very different from its neighbours" pop Wagner describes. Hoppe's rule (interpolate the normal with the same factor, renormalise) is the direct cure; if normals are unit-length and the renderer does not renormalise, a plain lerp with the same b followed by one normalise per morphing vertex is the cheapest acceptable approximation (the slerp Hoppe uses is unnecessary for the small angles between a midpoint normal and its endpoints' mean, inference).
- Equivalent and cheaper on a fixed-function path: lerp the Gouraud colour (the post-lighting per-vertex RGB) with the same b between the mean of the two endpoint colours and the midpoint's true colour. This matches de Boer's observation that the shading pop is only "slight" (so a linear colour blend is enough) and keeps the normal pipeline untouched; whether the I'76 hook point exposes colours before or after lighting is not known here.

### Gaps
- No source quantifies the visual magnitude of the Gouraud pop vs the geometric pop; de Boer's "only slightly noticeable" is the only judgement found.
- Röttger 1998 does not say whether its SGI implementation lit the terrain per vertex or used a texture; its figures show a texture-mapped height field, so the shading-pop question may simply not have arisen there (inference).

## Key question 5: merges (tiles leaving the ring as the camera retreats)

### Takeaway
Every distance- or position-driven variant (Röttger, de Boer, Ulrich, Strugar, Losasso & Hoppe) handles merges symmetrically because the factor is a pure function of the current camera position and reverses along the same ramp; only Hoppe 1998's time-based geomorph is asymmetric, needing special "one layer at a time" coarsening at half the refinement duration.

### Cited Findings
- Hoppe 1998: "Geomorph coarsening is more challenging within the VDPM framework. Unlike in geomorph refinement, the geometry interpolation must take place first, and only then can the mesh connectivity be coarsened ... we only allow geomorph coarsening 'one layer at a time' ... To help mitigate this delay, we reduce the gtime parameter for geomorph coarsening to half that for geomorph refinement. Fortunately, geomorph coarsening is required only when the viewer is moving backwards - a more infrequent situation." In the flythrough "the fraction of vertices undergoing geomorph refinement and coarsening is 26.8% and 0.2% respectively." — [Hoppe 1998, §4.2, Fig. 10 caption](https://hhoppe.com/svdlod.pdf)
- Losasso & Hoppe: "the transition is not time-based but instead tracks the continuous viewer position." — [Losasso & Hoppe 2004, §6.2](https://hhoppe.com/geomclipmap.pdf)
- Ulrich: "A node splits when f hits 0, and its children start at f = 1, so the transition is seamless" (fetch-tool paraphrase). — [Ulrich slides "morph"](https://tulrich.com/geekstuff/siggraph02-slides/text26.html)
- de Boer: t = (d - D_n)/(D_{n+1} - D_n) depends only on the current distance d. — [de Boer 2000, Equation 3](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Röttger: b = 2(1 - f) with f recomputed every frame from the current eye distance. — [Röttger 1998, §2.3](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)

### Inferences
- In a stateless per-frame rebuild, a merge is just the frame in which f crosses 1 the other way; the tile's midpoints were at b = 0 (on the parent edges) in the previous frame and are simply absent in this one, so no vertex visibly moves. The symmetry is automatic and there is nothing to add for retreat.
- Hysteresis (which the brief says the proxy has experimented with via the per-node hash) would break this symmetry: if split and merge thresholds differ, b must be defined relative to whichever threshold is active for that node this frame or the merge will pop. Simplest rule (inference): compute b from the merge threshold when the node was subdivided last frame and from the split threshold otherwise, which requires only the one-bit "was subdivided" memory the hash already provides.

### Gaps
- No source discusses geomorphing combined with split/merge hysteresis; the rule above is inference.

## Key question 6: reports of retrofitting geomorphing into an existing / old engine

### Takeaway
No written before/after report of geomorphing retrofitted into a 1990s engine via proxy or source port was found; the closest items are Wagner's 2003 measurements of adding CPU-side vs GPU-side morphing to a geomipmap engine, an early OpenMW (Ogre-era) terrain shader that carried an LOD morph factor per vertex, and community notes from 2005-era Irrlicht and GameDev.net threads; the Interstate '76 reimplementation found is Open76 (Unity), and no "I26" Godot project surfaced.

### Cited Findings
- Wagner 2003 is the one measured retrofit: adding software (CPU) morphing to a static-LOD geomipmap renderer dropped the minimum scene from 504 to 312 fps and the full scene from 231 to 205 fps; moving the morph into the vertex shader restored 501 / 230 fps. — [Wagner 2003, Table 1](https://www.ims.tuwien.ac.at/publications/tuw-138077.pdf)
- Early OpenMW (Ogre-based) terrain shader: "the target LOD which is being morphed to is stored in lodMorph.y, and the LOD at which the vertex should be morphed is stored in uv.w. It then offsets the vertex by a scaled amount only when the vertex's LOD is finer than the target" (search-result paraphrase; the mirror page itself returned 404 on fetch). An older OpenMW TerrainMesh class "handles building, destroying and LOD morphing for one cell" with an mLODMorphFactor member. — [OpenMW terrain.shader mirror](https://git.cijber.net/mirror/openmw/src/commit/1a771ae67150a2ed4539cdb44db40f0e4fe8097c/files/materials/terrain.shader), [OpenMW cpp_terrainmesh.cpp mirror](https://git.cijber.net/mirror/openmw/src/commit/c18a1ebd05e6ce7c862c3e49a27624028f102f23/terrain/cpp_terrainmesh.cpp)
- Irrlicht 2005 forum thread on a geomipmapped terrain node: terrain popping reported and "a vertex shader would be a reasonable fix"; "heightmaps producing plateaus or jagged hills make popping more noticeable" (search-result paraphrase). — [Irrlicht forum](https://irrlicht.sourceforge.io/forum/viewtopic.php?p=30648)
- A minimal open-source CDLOD demo (three.js) "handles morphing in its vertex shader", "automatically handles seams between tiles with different LODs", and notes its LOD selection "ignores height" and skips frustum culling. — [tschie/terrain-cdlod](https://github.com/tschie/terrain-cdlod)
- Interstate '76 reimplementation: Open76 is "a community engine reimplementation of Interstate '76 on Unity. It can parse and render nearly everything in a level, including cars. Driving and camera modes work, but the simulation does not work yet" (search-result paraphrase of mirrored README). — [Open76 mirror](https://ohotnik.duckdns.org/Nition/Open76)

### Inferences
- The absence of retrofit write-ups is itself informative: in every documented case the morph was added where the vertex stream is generated (the engine's own mesh builder or vertex shader), never by intercepting a finished vertex stream. The brief's situation (the proxy can hook the edge-split routine that writes midpoint heights) is the same insertion point Röttger uses, so the published method applies without a shader.
- Wagner's CPU-side penalty came from re-uploading a vertex buffer that was otherwise static; an engine that already rewrites its terrain vertices every frame pays none of that, so the expected cost is the per-midpoint lerp only (inference).

### Gaps
- No "I26" Godot reimplementation of Interstate '76 was found in two searches; either it is not indexed under that name or it does not exist publicly.
- No OpenRCT2 / Daggerfall Unity terrain-LOD morph notes were searched for separately (budget); none surfaced incidentally.
- The full text of the GameDev.net "Vertex morphing action" blog and the gamedev.net reprint of Wagner's article returned 403; only search snippets and the TU Wien PDF were used.

## Key question 7: cheapest variant for a hooked 1997 CPU renderer (synthesis)

### Takeaway
The cheapest published variant that matches a stateless per-frame quadtree is Röttger 1998's: reuse the split ratio f = eye distance / (C · tile size) already computed when the split is decided, set b = clamp(2(1 - f), 0, 1) for every midpoint the split creates, write height = parent_edge_mean + b · (true - parent_edge_mean) in the edge-split routine, store b per node in the existing per-node hash (one byte, refilled each frame) and take the min across any shared edge; add nothing to the vertex count, nothing across frames, and blend the Gouraud colour (or normal) with the same b to avoid the lighting pop de Boer and Wagner describe.

### Cited Findings
- Röttger's method stores only "the d2-values and blending factors" beyond the height data and runs the geomorph "at virtually no additional cost" on 1998 hardware at a fixed 25 Hz. — [Röttger 1998, abstract, §3-4](https://dspace.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- de Boer's morph needs only a per-level distance D_n per chunk and a per-vertex delta; his demo ran on a Pentium II 434 MHz. — [de Boer 2000, §3.1, §4](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- CDLOD requires Shader Model 3.0 for its canonical form and a precomputed-mesh-with-morph-deltas variant below that. — [Strugar 2009](https://github.com/fstrugar/CDLOD)
- Clipmaps need nested toroidal buffers updated incrementally and a vertex shader for the ~10-instruction alpha. — [Losasso & Hoppe 2004, §5-6](https://hhoppe.com/geomclipmap.pdf)
- Hoppe 1998 needs per-vertex cross-frame records and view extrapolation. — [Hoppe 1998, §4.2](https://hhoppe.com/svdlod.pdf)
- Ulrich needs precomputed chunk meshes with per-vertex morph deltas and skirts. — [Ulrich slides](https://tulrich.com/geekstuff/siggraph02-slides/text23.html)

### Inferences
- Against the brief's constraints: Ulrich (precomputed chunk meshes, skirts spending vertex indices), CDLOD (vertex shader or precomputed morph deltas), clipmaps (replaces the quadtree with nested grids) and Hoppe 1998 (cross-frame per-vertex state) each require either a different mesh structure or state the renderer does not keep. Röttger and de Boer both fit; Röttger fits better because its unit is the quadtree split (the same event the brief says is decided per tile per frame) rather than a fixed chunk with precomputed levels.
- Mapping Röttger's constants to the brief's split rule (inference): with "split when eye closer than 12.9 x size", C = 12.9 (or 18.3 on steep tiles), f = l / (C · d), and b = 2(1 - f) is 0 exactly at the split distance and 1 at half of it. Using the steep rule's 18.3 as C for those tiles keeps b continuous for them too, but a tile whose rule flips between 12.9 and 18.3 as its steepness classification changes would see b jump; the classification would need to be stable per tile (inference; the brief does not say whether it is).
- Vertex-index budget: the morph changes heights, not counts, so the 32,767 limit is unaffected; the only index-neutral alternative that also avoids the shared-edge bookkeeping is CDLOD's per-vertex factor computed from the midpoint's own distance, which the proxy could evaluate on the CPU in the edge-split routine (distance from eye to the midpoint, band = the parent's split range) at the cost of one distance per midpoint instead of one per node. Both are stateless; the per-vertex form removes the need for Röttger's min-across-edge step because a shared midpoint has one position and hence one factor from either side.
- Shading: apply the same b to the Gouraud colour (mean of endpoint colours -> true colour) or to the normal (lerp + normalise). Wagner's lightmap route is not available on a per-vertex Gouraud path without changing the texture pipeline, and Hoppe's slerp is unnecessary at these angles.

### Gaps
- Whether the hooked edge-split routine has access to both endpoint heights and colours / normals at the time it writes the midpoint, and whether the lighting pass runs before or after it, are I'76 facts not verified here.
- No published source gives a worked parameterisation for a 12.9x / 18.3x split rule; all constants for the retrofit are mappings (inference) from Röttger's C and from the brief.
