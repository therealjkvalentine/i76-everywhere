# Modern engine practice for heightfield terrain LOD and LOD-transition hiding (survey, 2026-10-21)

Scope: what current engines and notable titles do for heightfield terrain LOD, and which single component would transfer to a 1997 renderer hooked only from a DLL proxy (quadtree rebuilt every frame from the camera, split moment interceptable, per-vertex Gouraud, 32,767-vertex cap, 5 m heightfield, 1440p ultrawide at 120 Hz, 1,800-2,400 m view distance). Nothing below asserts anything about Interstate '76 itself beyond the brief; the I26 section quotes that project's own release notes.

Source-access notes (so the writer knows the evidence quality): the Frostbite GDC 2012 slide deck, the CDLOD paper and Hoppe's GPU Gems 2 chapter were downloaded and their text extracted locally with pdftotext; quotes from them are verbatim. Ulrich's SIGGRAPH 2002 chunked-LOD notes downloaded but the PDF's text layer is unreadable (font encoding), so the Ulrich formula is given only as inference. Epic's live documentation pages for the Landscape LOD settings are JavaScript-rendered and returned only a table of contents; the legacy docs.unrealengine.com and UDN hosts return 403/404 and web.archive.org is blocked from this tool, so Unreal's LOD-distribution semantics are documented here from the API reference tooltips (partly truncated) and a UE3-era search snippet. GDC Vault pages for Far Cry 5, Ghost of Tsushima, Witcher 3 and Frostbite were login-gated; only abstracts were readable. CryEngine's public source tree could not be fetched (404 on both `release` and `main` paths); CryEngine is covered only by unofficial sources.

## Key question 1: Per engine - LOD criterion, morphing, morph width, cracks, lighting across LOD

### Takeaway
Every modern heightfield renderer surveyed that documents its method uses a distance-doubling LOD ladder (equivalent to a constant screen-space triangle size) and hides the transition with a vertex-shader geomorph over a band at the outer edge of each LOD range, with cracks removed by index stitching or by making the morph itself seamless; lighting is taken from a normal map / heightmap texture, not from per-vertex normals, so it does not change when the geometry LOD changes.

### Cited Findings

**Unreal Engine 4/5 Landscape (non-Nanite path)**
- The LOD unit is the Landscape section ("These subsections are the base unit of Landscape LOD calculation"); sections are power-of-two sizes up to 256x256 vertices "so that different LOD levels can be stored in the mipmaps of the texture"; "Smaller Landscape Component sizes facilitate quicker LOD transitions and the occlusion of more terrain"; each section is a draw call; Epic recommends at most 1024 components. — [Epic, Landscape Technical Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-technical-guide-in-unreal-engine)
- LOD is chosen by screen size and a distribution curve, not by distance bands: ALandscapeProxy exposes `LOD0ScreenSize` ("This is the starting screen size used to calculate the distribution"), `LOD0DistributionSetting` ("The distribution setting used to change the LOD 0 generation, 1.25 is the normal distribution..." [tooltip truncated on the page]), `LODDistributionSetting` ("...3 is the normal distribution..." [truncated]), `MaxLODLevel` ("-1 means the max available"). The render system stores these as `LOD0ScreenSizeSquared`, `LOD1ScreenSizeSquared`, `LODOnePlusDistributionScalarSquared`. — [Epic API, ALandscapeProxy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Landscape/ALandscapeProxy); [Epic API, FLandscapeRenderSystem::LODSettingsComponent](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Landscape/FLandscapeRenderSystem/LODSettingsComponent)
- Transitions are continuous morphs in the vertex shader. UE5's own tooltips call it "continuous LOD morphing": `NonNaniteVirtualShadowMapConstantDepthBias` is a "Constant bias to handle the worst artifacts of the continuous LOD morphing when rendering to VSM", and `NonNaniteVirtualShadowMapInvalidationHeightErrorThreshold` exists because "cached VSM pages need to be invalidated when continuous LOD morphing introduces..." (truncated). — [Epic API, ALandscapeProxy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Landscape/ALandscapeProxy)
- Mechanism (UE3-era description, from a search-result excerpt of the UDN Landscape page; the page itself is no longer served): heightmaps are stored in textures so that two mip levels are sampled and their heights and offsets interpolated in the vertex shader, producing smooth transitions between LODs. The UE4 mobile vertex factory carries a per-vertex "Stream which has heights of each LOD levels" (`uint8[2*4] LODHeights`) for the same purpose on hardware without vertex texture fetch. — [UDN Three/Landscape (search snippet only)](https://udn.epicgames.com/Three/Landscape.html); [Epic API 4.26, FLandscapeVertexFactoryMobile::FDataType](https://docs.unrealengine.com/4.26/en-US/API/Runtime/Landscape/FLandscapeVertexFactoryMobile/FDataType/index.html)
- Epic's docs do not state the morph band width or the default pixel threshold anywhere reachable; a UE 5.6 forum thread shows users setting `LOD 0 Screen Size` = 10.0 with both distributions = 1.0 and seeing LOD misbehaviour, and a Japanese thread calls an LOD0 screen size of 1.25 "quite extreme". — [UE forum](https://forums.unrealengine.com/t/landscape-lod-distribution-broken-up-in-ue-5-6/2540379); [UE forum (JP)](https://forums.unrealengine.com/t/landscapelod-lod/2634495)
- Tessellation: the legacy D3D11 landscape tessellation properties (`TessellationComponentScreenSize` etc.) are absent from the current ALandscapeProxy API page; `ChangeComponentScreenSizeToUseSubSections` is deprecated ("has been ineffective for several versions now"). — [Epic API, ALandscapeProxy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Landscape/ALandscapeProxy)

**Unreal Engine 5 Nanite Landscape (5.3+; the page fetched is labelled 5.8)**
- Enabled per-Landscape with "Enable Nanite", then a build step ("Build Data"); Nanite landscapes "rely on standard Nanite techniques for LODs and vertex decimation"; "End users of your product should expect no visual improvement or downgrade since the source data is identical"; non-Nanite data is still streamed and kept ("This means twice the amount of data is streamed") because it is "required for Runtime Virtual Textures, water rendering, and more"; Nanite tessellation needs a displacement in the material; "Nanite skirts" (an extra row of edge vertices pushed down by a set depth) prevent seams between proxies at distance. — [Epic, Using Nanite with Landscapes](https://dev.epicgames.com/documentation/unreal-engine/using-nanite-with-landscapes-in-unreal-engine)

**Unity Terrain**
- The only geometry-LOD knob is Pixel Error. Script reference: `heightmapPixelError` is "An approximation of how many pixels the terrain will pop in the worst case when switching lod" and "A higher value reduces the number of polygons drawn." — [Unity ScriptRef, Terrain.heightmapPixelError](https://docs.unity3d.com/ScriptReference/Terrain-heightmapPixelError.html)
- Manual wording: Pixel Error "Simplifies the generated terrain to optimize rendering", lower values keep it "more faithful" at higher cost; Base Map Dist. is "The maximum distance to render textures in full resolution", beyond it "a lower resolution composite image" is used (this is a texture, not geometry, far LOD). — [Unity Manual, Terrain settings](https://docs.unity3d.com/Manual/terrain-OtherSettings.html)
- `enableHeightmapLODFrustumCulling` (on by default): patches outside the frustum are simplified aggressively; with it off "terrain is tessellated based on camera distance and pixel error only". — [Unity ScriptRef](https://docs.unity3d.com/ScriptReference/Terrain-enableHeightmapLODFrustumCulling.html)
- Default values: the brief's "Unity default 5 px" could not be confirmed from any official page fetched (the ScriptRef example sets 10; no page states the default). Base Map Distance default 1000 is reported by a forum user, not by the manual. — [Unity Discussions](https://discussions.unity.com/t/distant-terrain-looks-pixelated/430167)
- Unity does NOT morph: the pixel-error wording ("how many pixels the terrain will pop") is a popping budget, and cracks between neighbouring terrain tiles at different LOD are a known artifact fixed by `Terrain.SetNeighbors()` (third-party troubleshooting blog). — [bugnet.io](https://bugnet.io/blog/fix-unity-terrain-holes-appearing-at-chunk-boundaries)

**Frostbite (Battlefield 3, GDC 2012, Mattias Widmark)** - verbatim slide text
- Scalability target: "Arbitrary view distance (0.06m to 30 000m)", "Arbitrary level of detail (0.0001m and lower)"; "It is all about hierarchies!"; "Quadtree hierarchies used for all spatial representations"; "Frostbite approach similar to flight simulators". — [GDC12 slides PDF](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)
- LOD criterion: quadtree node payloads; "Nodes closer to root represent lower detail"; mesh: "Rendered in patches of 16x16 triangle pairs", "Projected triangle size rougly constant - support destruction everywhere", "Blocky crestlines (on console)"; heightfield "sampled in vertex shader" on PC/Xbox 360, stored as vertex attribute on PS3 because "Vertex shader texture fetch is too slow". — same
- Cracks: "Mesh stitching - A job analyze mesh quadtree and detect LOD switch edges - Edges are stitched by index permutations - Vertices are unchanged" (slide shows "No stitch / Stitch left / Stitch left and bottom"). — same
- Geometry morphing: the deck contains no vertex geomorph; its "CLOD" is a texture cross-fade in the virtual-texture indirection ("RGBA8 ... Index X, Index Y, Scale, CLOD fade"; "Used to smoothly fade in a newly composited tile (fade-to tile)"; "CLOD factor updated each frame"; "CLOD to smooth most streaming LOD transitions"). — same
- Lighting across LOD: with DX11 tessellation, "Displacement mapping from heightfield - No additional memory needs (heightfield used as normal map)"; tessellation "Tries to maintain a constant screen-space triangle width". Detail splats are view-limited: "Have to limit detail view distance - Typically 50m-100m". — same
- Heightfield tile is 133x133x2 bytes; raster tiles are 256x256 with a two-pixel border; streaming stops "when raster is slightly blurry (texel covers 2x2 pixels)". — same

**CDLOD (Strugar 2010; the reference quadtree-plus-morph design that Godot/Terrain3D-class engines cite)** - verbatim
- Criterion: 3D distance, with ranges doubling: "the difference in distance covered by them needs to be close to 2.0 to accomplish relatively even screen triangle distribution"; "the range of each level being two times larger than that of the previous one, and the range of the final level ... representing the required total viewing distance". — [CDLOD paper (fstrugar/CDLOD, cdlod_paper_latest.pdf)](https://github.com/fstrugar/CDLOD)
- Morph width: "the morph area is also defined, marking the range along which a higher complexity mesh will morph into the lower one. This morph area usually covers the last 15%-30% of every LOD range." — same
- Morph mechanism: "each vertex is morphed individually based on its own LOD metric unlike the method in [Ulrich 02], where the morph is performed per-node (per-chunk)"; "every block of eight triangles from the more detailed mesh is smoothly morphed into the corresponding block of two triangles on the less detailed mesh by gradual enlargement of the two triangles and reduction of the remaining six triangles into degenerate triangles"; morphK ranges "between 0 (no morph, high detail mesh) and 1 (full morph, four times fewer triangles)"; a morph vertex is "a grid vertex having one or both of its grid indices (i, j) as an odd number" moved toward neighbour (i - i/2, j - j/2); HLSL: `return vertex.xy - fracPart * g_quadScale.xy * morphK;`; "the z-component is obtained by sampling the heightmap ... using a bilinear filter (filtering is only needed for vertices in the morph region)". — same
- Cracks: "This process produces smooth transitions with no seams or T-junctions"; "no need for stitching meshes"; the requirement is that edge vertices stay identical between neighbours, so the morph distance must come from "a function ... consistent over the whole dataset domain". — same
- Trade-off statement on morph width: "The size of the morph area can also be decreased to mitigate this problem, but that can make the transition between levels noticeable." — same
- Lighting: datasets carry "a heightmap, normal map, overlay images"; shading uses "normals from the high resolution normalmap texture". — same
- CPU-only variant explicitly described for pre-SM3 hardware: "merging the CDLOD and ChunkedLOD [Ulrich 02] techniques ... Each vertex can contain additional morph data so that during the LOD transition some vertices can be moved into neighbouring ones". — same

**Geometry clipmaps (Losasso/Hoppe; GPU Gems 2 ch. 2; the basis of Terrain3D and REDengine 3's terrain)** - verbatim
- Criterion: nested rings around the viewer; "The aim is to maintain triangles that are uniformly sized in screen space. With a clipmap size n = 255, the triangles are approximately 5 pixels wide in a 1024x768 window." — [Hoppe, gpugcm.pdf](https://hhoppe.com/gpugcm.pdf)
- Goal statement: "hide the boundaries between successive resolution levels, while at the same time maintaining a watertight mesh and avoiding temporal popping artifacts ... introduce a transition region near the outer perimeter of each level, whereby the geometry and textures are smoothly morphed to interpolate the next-coarser level". — same
- Morph width and formula: "w is the transition width (chosen to be n/10)"; alpha "evaluates to 0 except in the transition region, where it ramps up linearly to reach 1 at the outer perimeter"; "z = (1 - alpha) zf + alpha zc" with zc "obtained by averaging the two coarse samples on the edge endpoints"; zc is precomputed at clipmap update to avoid extra vertex-texture reads. — same
- Cracks: "we render a string of degenerate triangles ... on the outer perimeter. These zero-area triangles are necessary to avoid mesh T-junctions." — same
- Lighting across LOD: "We let the normal map have twice the resolution of the geometry, because one normal per vertex is too blurry"; "the shader looks up the normals for the current level and the next-coarser level and blends them using the alpha value computed in the vertex shader". — same

**Godot 4 - Terrain3D (Tokisan)**
- "This is a Geomorphing Geometric Clipmap Mesh Terrain, as used in The Witcher 3"; "several flat meshes, which have a higher density towards the center, and lower farther away"; "The LODs are then blended together in a circular pattern"; meshes are centred on the camera; "Even though the meshes are constantly moving, the terrain appears stable because the height data remains fixed in place." — [Terrain3D docs, Introduction](https://terrain3d.readthedocs.io/en/stable/docs/introduction.html)
- "Up to 10 levels of detail for the terrain mesh"; terrain from 64x64 m to 65.5x65.5 km. — [Terrain3D README](https://github.com/TokisanGames/Terrain3D)
- 1:1 heightmap-pixel-to-LOD0-vertex, `vertex_spacing` to stretch it; mesh components are "generated once" and recentred, the vertex shader reads heights so the mesh is never regenerated; references given are Mike J. Savage's clipmap article, GPU Gems 2 ch. 2 and the GDC 2014 Witcher 3 talk. — [Terrain3D docs, System Architecture](https://terrain3d.readthedocs.io/en/stable/docs/system_architecture.html)
- The docs do not state the ring count, morph band width or seam method; those live in the shader source (not fetched).

**Godot 4 - Zylann HTerrain**
- Quadtree of 32x32 (or 16x16) chunks, "chunk size can be scaled by a power of two depending on the distance from the camera"; "If a group of 4 chunks are far enough, they will join into a single one. If a chunk is close enough, it will split in 4 smaller ones"; `lod scale` is "a factor determining at which distance chunks will split or join" (distance-based, no screen-error metric); "the quad tree is updated on the CPU". — [HTerrain docs](https://hterrain-plugin.readthedocs.io/en/latest/)
- Cracks: "transitions between LODs are seamless" via precomputed mesh variants "chosen by which LOD their neighbors use" (index stitching, no vertex morph mentioned); memory cost grows with chunk size "due to all chunk variants that are precalculated". — same
- Lighting: normals are baked to a texture as you sculpt, which "allows for levels of detail to work without affecting perceived quality too much". — same

**Godot 4 core (not terrain-specific, but the engine's own LOD thresholds)**
- Mesh LOD "uses a screen-space metric"; project setting "Rendering > Mesh LOD > LOD Change > Threshold Pixels", "The default mesh LOD threshold of 1 pixel is tuned to look" perceptually lossless; "Higher camera FOV and lower viewport resolutions will make LOD selection more aggressive." — [Godot docs, Mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- Visibility ranges have explicit hysteresis: Begin/End Margin is "The hysteresis or alpha fade transition distance"; "This prevents situations where LOD levels are switched back and forth quickly"; fade mode Disabled "Uses hysteresis to switch between LOD levels instantly", Self/Dependencies "Uses alpha blending to smoothly fade between LOD levels" at a cost ("forces transparent rendering"). — [Godot docs, Visibility ranges](https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html)

**O3DE (Open 3D Engine) terrain** - a current engine that publishes its CLOD numbers
- "First LOD distance" default 128.0 m ("The distance in meters from the camera that the first LOD renders to"); "Subsequent LODs are located at double the distance from the previous LOD" with half the resolution; "Continuous LOD" default Enabled ("smoothly blends geometry between terrain LODs"); "CLOD Distance" default 16.0 m ("Distance in meters over which the first LOD blends into the next LOD. Subsequent LODs blend over double the distance"); "We recommend this value is less than about 25% of First LOD distance"; "If set too low, then seams may appear in the terrain." — [O3DE docs, Terrain World Renderer](https://docs.o3de.org/docs/user-guide/components/reference/terrain/world-renderer/)

**Cesium (geospatial; the canonical published screen-space-error convention)**
- `Globe.maximumScreenSpaceError` default 2: "The maximum screen-space error used to drive level-of-detail refinement. Higher values will provide better performance but lower visual quality." — [CesiumJS ref, Globe](https://cesium.com/learn/cesiumjs/ref-doc/Globe.html)
- 3D Tiles spec: geometric error is "the error, in meters, introduced if this tile is rendered and its children are not"; SSE is "the error measured in pixels", computed from geometric error plus "distance from the tile to the camera, screen size, and resolution"; "If the introduced SSE exceeds the maximum allowed, then the tile is refined". — [3D Tiles spec](https://github.com/CesiumGS/3d-tiles/blob/main/specification/README.adoc)

### Inferences
- The field has converged: distance-doubling ladder (= constant screen triangle size), vertex geomorph band of 10-30 % of each LOD range (Hoppe n/10 per ring; CDLOD "last 15%-30%"; O3DE 16 m of 128 m = 12.5 %, "less than about 25 %"), cracks by index stitching (Frostbite, HTerrain) or morph-to-exact-parent (CDLOD, clipmaps), and shading from a texture (normal map / heightfield-as-normal-map) so geometry LOD never changes lighting. Unity is the outlier that documents a popping budget in pixels and no morph.
- Frostbite is the one AAA deck here with no geometry morph at all: a constant projected triangle size plus index-permutation stitching was judged sufficient (and "blocky crestlines" accepted on console). That is an existence proof that stitching + fine-enough geometry can ship without geomorph.
- The Witcher 3 / Terrain3D "stable because the height data remains fixed in place" statement is the clipmap answer to temporal stability: topology moves with the camera, but every rendered height is a fixed sample, so nothing wobbles between frames except inside the explicit morph bands.

- Unreal's exact morph-band width and the meaning of "1.25 / 3 normal distribution" could not be read (pages JS-rendered; legacy hosts 403/404; archive.org blocked).
- Unity's default Pixel Error (commonly stated as 5) is unconfirmed by any official page fetched.
- CryEngine official LOD documentation and source unreachable; Far Cry 5, Witcher 3 and Tsushima slides login-gated.
- No primary source for Rage, RDR2, HZD or MSFS terrain LOD transitions.

## Key question 2: What "pixel error" / screen-space-error values are used, what they mean at 1440p, and how that compares with a world-space threshold growing with distance squared

### Takeaway
Published tolerances cluster at 1-5 px (Godot mesh LOD 1 px default; Cesium 2 px default; Ulrich's 2002 demo "around 2-pixel"; Hoppe's clipmap designed for ~5 px triangles at 1024x768), and the metric is linear in geometric error over distance, scaled by viewport width over field of view, so the same tolerance is stricter in world terms at 3440 px than it was at 1024 px.

### Cited Findings
- Godot: "The default mesh LOD threshold of 1 pixel is tuned to look" perceptually lossless; "Higher camera FOV and lower viewport resolutions will make LOD selection more aggressive." — [Godot docs, Mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- Cesium: `maximumScreenSpaceError` default 2 (pixels). — [CesiumJS ref, Globe](https://cesium.com/learn/cesiumjs/ref-doc/Globe.html)
- 3D Tiles: SSE in pixels is computed from geometric error (metres), camera distance, screen size and resolution; refinement happens when SSE exceeds the maximum allowed. — [3D Tiles spec](https://github.com/CesiumGS/3d-tiles/blob/main/specification/README.adoc)
- Ulrich chunked LOD demo (23 June 2002 entry): "rendered here w/ around 2-pixel screen-space error tolerance", geometry processed "with a 4 meter object-space error tolerance". — [tulrich.com chunklod page](http://tulrich.com/geekstuff/chunklod.html)
- Hoppe: n = 255 clipmap gives triangles "approximately 5 pixels wide in a 1024x768 window". — [Hoppe, gpugcm.pdf](https://hhoppe.com/gpugcm.pdf)
- Unity: pixel error = "how many pixels the terrain will pop in the worst case when switching lod". — [Unity ScriptRef](https://docs.unity3d.com/ScriptReference/Terrain-heightmapPixelError.html)
- Cesium terrain-provider style quality knobs: "a value of 0.5 halves the estimated level-zero geometric error, allowing twice the screen pixels between adjacent heightmap vertices" (search snippet of a Cesium TerrainProvider doc; not independently fetched). — [Cesium b28 TerrainProvider doc](https://cesium.com/downloads/cesiumjs/releases/b28/Documentation/TerrainProvider.html)
- Screen-space error definition as taught (course notes restating Ulrich): "the difference between the screen projections of high- and low-detail geometry", conservatively approximated from each chunk's precomputed maximum geometric error, the viewer distance to the chunk bounds and the field of view (search snippet; the PDF itself failed on an expired certificate). — [UChicago CS23700 project 4](https://classes.cs.uchicago.edu/archive/2014/winter/23700-1/project_4_and_5/project-04.pdf)

### Inferences
- (Inference, standard derivation; Ulrich's PDF text was unreadable so this is not quoted) rho_px = delta_m / D_m * K, with K = W_px / (2 tan(hfov/2)). At 3440 px wide with a 90-degree horizontal FOV, K = 1720 px; at 1024 px wide and the same FOV, K = 512. So a 2 px budget at 3440 px tolerates delta/D = 1/860: 1 m of height error at 860 m, 2.1 m at 1,800 m, 2.8 m at 2,400 m. The same 2 px at 1024 px tolerated 3.4x more world error. If the engine's FOV is narrower the K is larger still (K scales as 1/tan(hfov/2)). The I'76 FOV is not known to this note; recompute with the real value.
- (Inference) The 1-2 px tolerances in Godot/Cesium are "sub-threshold" budgets: error that small is hidden by the pixel grid, which is why those engines do not need geomorph for meshes/tiles. Unity's larger values are visible pops by its own definition.
- (Inference) A split test of the form "geometric error > c * D^2" is more permissive than SSE at range (SSE is linear in D). Over 1,800-2,400 m such a rule would let 2.5-5 m errors through where a 2 px SSE at 3440 px allows about 2-3 m; over 300-600 m it would be far stricter than SSE (under 0.5 m where SSE allows 0.7-1.4 m). A D^2 rule therefore spends vertices near and pops far - the opposite of the modern allocation. A D^1 (SSE) rule with a constant pixel budget is the published norm.

### Gaps
- No engine publishes a terrain-specific default pixel error with its FOV convention (vertical vs horizontal, which matters on ultrawide); Godot and Cesium state defaults but not the K formula they use.
- Unity's default Pixel Error unconfirmed.

## Key question 3: Why not "coarser everywhere beyond some distance"? Does any engine use a single far LOD, and what does it look like?

### Takeaway
Engines reject a single far LOD because the goal they state is a constant screen-space triangle size (Frostbite, Hoppe, CDLOD) so that vertex budget tracks what the eye can resolve; the documented single-distance switches that do exist are texture-side (Unity Base Map Distance, Frostbite detail splats to 50-100 m, Yotei baked far mountains), and the one documented single-boundary geometry LOD in a heightfield renderer (I26 v0.6.0) produced visible seams and holes at the boundary that were then tuned by pushing the boundary out.

### Cited Findings
- Frostbite's design goal: "Projected triangle size rougly constant"; tessellation "Tries to maintain a constant screen-space triangle width". — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)
- Hoppe: "The aim is to maintain triangles that are uniformly sized in screen space." — [Hoppe](https://hhoppe.com/gpugcm.pdf)
- CDLOD: ranges "calculated with the goal of producing approximately the same average number of triangles per square unit of screen over the whole rendered terrain". — [CDLOD paper](https://github.com/fstrugar/CDLOD)
- CDLOD on what a narrow transition looks like: reducing the morph area "can make the transition between levels noticeable"; mismatched settings "can appear in the form of seams between LOD levels". — same
- O3DE: too small a CLOD distance means "seams may appear in the terrain". — [O3DE docs](https://docs.o3de.org/docs/user-guide/components/reference/terrain/world-renderer/)
- Single-distance switches that are texture-only: Unity Base Map Distance (full-resolution textures to a distance, "lower resolution composite image" beyond). — [Unity Manual](https://docs.unity3d.com/Manual/terrain-OtherSettings.html); Frostbite detail splats "Have to limit detail view distance - Typically 50m-100m". — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf); Ghost of Yotei bakes distant terrain into textures. — [PlayStation Blog](https://blog.playstation.com/?p=411201)
- A shipped single-boundary geometry LOD and its artifacts (I26 v0.6.0 release notes, Godot reimplementation of I'76): "the ground a kilometre or more away is drawn with coarser triangles (10 m, then 20 m between points"; the same release fixed "holes and thin slits through the far ground (#63, #65) where the white sky showed" and "a thin light seam up a hillside or canyon wall, where the sky showed through a hairline crack" between chunks of different detail, by moving the boundary: "The 2.5 m level now holds until 360 m and gives way at 450 m (it was 320 m)". — [I26 releases (GitHub API)](https://api.github.com/repos/vahokif/I26/releases); [I26 #63](https://github.com/vahokif/I26/issues/63); [I26 #67](https://github.com/vahokif/I26/issues/67)
- MSFS users describe the result of coarse far rings with no fade as pop-in noticeable "when panning the camera around" and ask for "some type of LOD fading system". — [MSFS forum](https://forums.flightsimulator.com/t/implement-some-type-of-lod-fading-system-to-help-reduce-terrain-and-object-pop-in/523441)

### Inferences
- (Inference) With a fixed vertex cap, "coarser everywhere beyond R" wastes the budget: all terrain inside R costs full density whether 10 m or 900 m away, and everything past R jumps in one step, so the silhouette error at R is the whole difference between two grid spacings at once. The doubling ladder spreads the same budget so each ring's error is roughly the same number of pixels.
- (Inference from the I26 notes) The visible symptoms of a hard band edge in a Gouraud heightfield are: hairline cracks where a fine chunk meets a coarse one on a slope (T-junctions), sky showing through when looking down from high ground, and a crest-line step that walks toward the viewer as the band edge moves with the camera. Pushing the edge out (320 -> 450 m) reduced the frequency, not the mechanism.

### Gaps
- No modern engine documentation was found that defends a single far geometry LOD; the only documented example is I26, whose source is not yet published ("Please stand by...").

## Key question 4: Which components are inherently GPU-side (unavailable to a fixed-function / software vertex path) and which are CPU-side and cheap

### Takeaway
Everything that hides transitions in modern engines is a per-vertex height blend or a per-pixel normal blend computed in a shader, but the height blend itself is pure arithmetic on data the CPU already has at the moment a tile is split, and both CDLOD and Hoppe describe CPU-side forms of it; what cannot transfer is per-pixel normal blending, hardware tessellation and Nanite.

### Cited Findings
- GPU-side by construction: Hoppe computes alpha and z = (1-alpha)zf + alpha zc "in the vertex shader" and blends normals in the pixel shader. — [Hoppe](https://hhoppe.com/gpugcm.pdf); CDLOD morphs "in the vertex shader" and targets "Shader Model 3.0 generation and above". — [CDLOD paper](https://github.com/fstrugar/CDLOD); UE's continuous LOD morphing is a vertex-factory function and its mobile path carries per-vertex LOD heights. — [Epic API](https://docs.unrealengine.com/4.26/en-US/API/Runtime/Landscape/FLandscapeVertexFactoryMobile/FDataType/index.html); Frostbite DX11 tessellation uses hull/domain shaders. — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf); Nanite landscape is a GPU-virtualized mesh with its own decimation. — [Epic, Nanite landscapes](https://dev.epicgames.com/documentation/unreal-engine/using-nanite-with-landscapes-in-unreal-engine)
- CPU-side precedents documented by the same authors: CDLOD's "Performance on older hardware" section describes, for Shader Model 2 or lower, pre-tessellated meshes with "additional morph data so that during the LOD transition some vertices can be moved into neighbouring ones", a per-vertex operation that needs only the vertex's own LOD metric. — [CDLOD paper](https://github.com/fstrugar/CDLOD); Hoppe precomputes the coarse height zc during the CPU-side clipmap update rather than in the shader ("we compute zc as part of the clipmap update"). — [Hoppe](https://hhoppe.com/gpugcm.pdf); HTerrain's quadtree with stitched chunk variants is CPU-driven ("the quad tree is updated on the CPU"). — [HTerrain docs](https://hterrain-plugin.readthedocs.io/en/latest/)
- CPU-side crack fixes: Frostbite's stitching is "Edges are stitched by index permutations - Vertices are unchanged", done in a CPU job. — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf); Nanite landscape skirts are "an added row of edge vertices pushed down by a set depth". — [Epic, Nanite landscapes](https://dev.epicgames.com/documentation/unreal-engine/using-nanite-with-landscapes-in-unreal-engine)
- Screen-space error tests and hysteresis are CPU decisions in every engine that documents them (Cesium refinement test; Godot visibility-range margins). — [3D Tiles spec](https://github.com/CesiumGS/3d-tiles/blob/main/specification/README.adoc); [Godot visibility ranges](https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html)
- Texture-side transition hiding (not geometry): Frostbite's CLOD fade of virtual-texture tiles. — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)

### Inferences
- (Inference) Mapping the brief's candidates onto the above: vertex morph band = CPU-feasible at the split hook (write h = (1-k)*parent_edge_midpoint + k*true_height for each new odd vertex, with k from the node's own distance within its LOD range; CDLOD's "consistent function" requirement means k must be computed from the same anchor data neighbours see, otherwise edge vertices disagree and cracks appear). Hysteresis = CPU-only but needs cross-frame state, which the brief says the quadtree does not keep (it could be reconstructed from the camera distance alone, since the quadtree is deterministic in the camera; a one-frame store of "split distance per node key" is the minimum state). Screen-space error threshold = a constant to patch if the split test already divides by distance; if the split test is a world-space threshold it needs the formula swapped, which is a code change not a constant. Skirts = extra vertices against a 32,767 cap; Frostbite's index-permutation stitching costs no vertices but needs index-buffer access at the split hook. Normal maps = unavailable in a Gouraud path; the CPU analogue is to keep each vertex's lighting from a fixed-resolution source (the 5 m heightfield normal at that vertex) regardless of which LOD created it, which is what "height data remains fixed in place" buys clipmaps. Fog/haze = a constant.
- (Inference) The one thing the 1997 path cannot copy at all is per-pixel normal blending; with Gouraud, a morphed vertex whose colour is also interpolated between parent and child lighting is the exact CPU analogue of Hoppe's alpha-blended normals, at zero extra vertices.

### Gaps
- No source quantifies the CPU cost of a per-vertex morph at split time; CDLOD's older-hardware variant is described, not benchmarked.

## Key question 5: Published numbers on acceptable transition visibility (pixels moved per frame, morph duration in frames or metres)

### Takeaway
The literature specifies transition width in distance, not in frames or pixels-per-frame: Hoppe n/10 of each ring, CDLOD 15-30 % of each LOD range, O3DE 16 m of the first 128 m and doubling per level (with "< 25 %" guidance); acceptable static error is stated as 1-2 px (Godot, Cesium, Ulrich) and no source gives a per-frame pixel-velocity limit.

### Cited Findings
- Hoppe: transition width "chosen to be n/10", alpha "ramps up linearly" over it. — [Hoppe](https://hhoppe.com/gpugcm.pdf)
- CDLOD: "This morph area usually covers the last 15%-30% of every LOD range"; shrinking it "can make the transition between levels noticeable". — [CDLOD paper](https://github.com/fstrugar/CDLOD)
- O3DE: CLOD Distance default 16.0 m against First LOD distance 128.0 m, doubling per LOD; "less than about 25% of First LOD distance"; too low gives seams. — [O3DE docs](https://docs.o3de.org/docs/user-guide/components/reference/terrain/world-renderer/)
- Godot mesh LOD 1 px default is called perceptually lossless. — [Godot docs](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- Cesium 2 px default. — [CesiumJS ref](https://cesium.com/learn/cesiumjs/ref-doc/Globe.html)
- Ulrich 2002 demo "around 2-pixel screen-space error tolerance". — [tulrich.com](http://tulrich.com/geekstuff/chunklod.html)
- Unity's pixel error is defined as worst-case pop in pixels, so whatever a project sets is its accepted pop. — [Unity ScriptRef](https://docs.unity3d.com/ScriptReference/Terrain-heightmapPixelError.html)
- Godot's hysteresis margins exist to stop LOD "switched back and forth quickly", but no numeric default is given on the page. — [Godot visibility ranges](https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html)

### Inferences
- (Inference) Converting distance bands to time: at a driving speed of 30 m/s, a CDLOD-style band that is 20 % of a 450 m LOD range (90 m) is crossed in 3 s = 360 frames at 120 Hz, so each vertex moves about 1/360 of its total LOD error per frame; with a 2-3 px total error that is under 0.01 px per frame, i.e. invisible. The same error popped in one frame is a 2-3 px step, which is what the Unity definition calls a pop. The point of the band is to spread a fixed total displacement over hundreds of frames, not to reduce it.
- (Inference) For the brief's ranges (1,800-2,400 m view distance on a 5 m grid), a doubling ladder from 5 m has about 8-9 levels; the outermost band at 15-30 % of ~1,000 m is 150-300 m wide, the innermost at 15-30 % of ~50 m is 7-15 m wide.

### Gaps
- No source gives a threshold in pixels moved per frame or a morph duration in frames; all are distance fractions.

## Key question 6: What the I26 project (Godot reimplementation of Interstate '76) says about its terrain LOD and draw distance

### Takeaway
I26's release notes (v0.4.0-v0.7.0, Oct 2026) document a "Far" draw distance of 20 km versus the original's 600 m, a two-step distance-bucketed far LOD (10 m then 20 m spacing beyond about 1 km, with the 2.5 m level held to 360 m and handed over at 450 m), and a sequence of fixes for holes, hairline cracks on slopes and a distant-mountain-ring backstop - a worked example of the artifacts a hard LOD band produces.

### Cited Findings
- Project: "Godot engine reimplementation of Interstate '76", "Modernized graphics" plus a "1997 mode" toggled with F12; source "Please stand by..."; requires the GOG game and Nitro Pack. — [I26 README](https://github.com/vahokif/I26)
- v0.4.0 (2026-10-11): "Original clips at the original's 600 m in either look; Far, the default, draws to 20 km as before." — [I26 releases](https://api.github.com/repos/vahokif/I26/releases)
- v0.6.0 (2026-10-15): "the ground a kilometre or more away is drawn with coarser triangles (10 m, then 20 m between points"; "Modern look at the Far draw distance is lighter to draw (#34)"; fixed "holes and thin slits through the far ground (#63, #65) where the white sky showed"; fixed "a thin light seam up a hillside or canyon wall, where the sky showed through a hairline crack" between chunks of different detail; "The 2.5 m level now holds until 360 m and gives way at 450 m (it was 320 m)"; "The distant mountain ring runs under the map as a backstop", previously "flat-shaded, low-poly terrain poking through the real ground near the map's edge" and "its coarse cells at the map's edge could stand above the modern terrain's cliff faces", now "drawn over the map only where it is under the lowest ground near each 10 m of it"; "Pieces of the distant mountain ring were being dropped from the picture while still in view"; in 1997 look "a strip of sky no longer shows between the ground and the background mountains where the map's ground ends". — same
- v0.6.1 (2026-10-16): "the distant mountain ring drawn over everything, around and in front of the car, on some graphics drivers" (depth write fix). — same; matching issue: "With the far draw distance enabled in the modern renderer, the 3D backgrounds are visible everywhere." — [I26 #69](https://github.com/vahokif/I26/issues/69)
- v0.7.0 (2026-10-19): 1997-look horizon mountains "broke into vertical blocks at different heights that jumped up and down as you drove", fixed so their foot follows the ground edge; Nitro arenas "showed a white band where the mountains should be", now plain sky and haze; bridge/ramp shadows "fall on the terrain under them, vertex by vertex"; "no shadow plane is ever steeper than 45 degrees". — [I26 releases](https://api.github.com/repos/vahokif/I26/releases)
- Issue wording for the holes: "in some area you can see 'slit' gaps on the terrain where you can see the empty white void" (#63) and "The textures, depending on the terrain and its shape unfortunately shows a gap" (#67), both closed. — [I26 #63](https://github.com/vahokif/I26/issues/63); [I26 #67](https://github.com/vahokif/I26/issues/67)
- 1997-mode gap: "there's a gap between the ground and the background mountains in 1997 hardware mode" (#46, closed). — [I26 #46](https://github.com/vahokif/I26/issues/46)

### Inferences
- (Inference) I26's far LOD is a distance-bucketed fixed table (2.5 m to 360/450 m; 10 m from about 1 km; 20 m beyond), not a screen-space metric, and the notes mention no morph; the fixes were boundary moves and a backstop mesh, which is consistent with the "hard band edge" symptoms in question 3. The "holds until 360 m and gives way at 450 m" wording reads like a hysteresis pair (hold-until vs give-way-at), though the notes do not call it that.
- (Inference) 20 km in I26 is sky/mountain-ring plus coarse ground; the brief's 1,800-2,400 m target is an order of magnitude shorter, so I26's 10 m/20 m buckets would sit mostly beyond the target range.

### Gaps
- I26 source is unpublished; whether the Godot build uses Terrain3D, HTerrain or a custom mesh is not stated anywhere fetched. "Seams on steep slopes" in the brief maps to the v0.6.0 "hairline crack up a hillside or canyon wall" note; no separate steep-slope seam issue was found.

## Synthesis for the brief: the single component that transfers

### Takeaway
The one modern component that is both the field's consensus transition-hider and implementable purely at the split hook with no GPU support and no cross-frame state is the vertex morph band (geomorph): write each newly created split vertex's height (and its Gouraud colour) as a blend between the parent edge midpoint and the true heightfield value, with the blend factor taken from the node's distance within its LOD range, using a band of roughly 15-30 % of each range; this is what CDLOD, geometry clipmaps, REDengine 3, Terrain3D, O3DE and Unreal's non-Nanite path all do, and it is exactly the CPU variant CDLOD describes for pre-shader hardware.

### Cited Findings
- Consensus and widths: Hoppe n/10 ring band with linear ramp and blended normals; CDLOD last 15-30 % per range, per-vertex morph, no stitching needed; O3DE CLOD 16 m of 128 m, doubling, "< about 25 %"; Unreal "continuous LOD morphing"; Terrain3D "Geomorphing Geometric Clipmap ... as used in The Witcher 3". — [Hoppe](https://hhoppe.com/gpugcm.pdf); [CDLOD](https://github.com/fstrugar/CDLOD); [O3DE](https://docs.o3de.org/docs/user-guide/components/reference/terrain/world-renderer/); [Epic API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Landscape/ALandscapeProxy); [Terrain3D](https://terrain3d.readthedocs.io/en/stable/docs/introduction.html)
- CPU form exists in the literature: CDLOD "Performance on older hardware" (per-vertex morph data on SM2-or-lower) and Hoppe's precomputed coarse height zc. — [CDLOD](https://github.com/fstrugar/CDLOD); [Hoppe](https://hhoppe.com/gpugcm.pdf)
- The alternative that ships without morph is Frostbite's: constant projected triangle size plus index stitching, accepting "Blocky crestlines (on console)". — [GDC12 slides](https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf)
- The alternative that ships with a hard band (I26) needed hole, crack and backstop fixes and boundary moves. — [I26 releases](https://api.github.com/repos/vahokif/I26/releases)

### Inferences
- (Inference) Why morph over the other candidates, given the constraints: it adds zero vertices (skirts do not); it needs no frame-to-frame state (hysteresis does) because the blend factor is a pure function of camera distance, which the per-frame quadtree rebuild already has; it is independent of whether the split criterion is distance or screen error, so it can ship before any threshold work; and because the quadtree is rebuilt every frame from the camera, a hard split already flips between two exact topologies per frame, so the morph's only job is to make the new vertices start where the old surface was and move continuously, which is the CDLOD/Hoppe guarantee ("exactly matches the one from the lower LOD layer; hence it can be seamlessly replaced by it").
- (Inference) Preconditions it imposes, from the CDLOD seam discussion: the blend factor for an edge vertex must be computed from data both neighbours agree on (the same distance function on the same anchor), or cracks appear along chunk edges; and the band should not be narrowed below about 15 % of the range to save work, since both CDLOD and O3DE warn that is where transitions become "noticeable" or seams appear.
- (Inference) Second component, if one more is allowed: a screen-space-error split constant (1-3 px at 3440 px, with K recomputed for the engine's real FOV), because the world-space-growing-with-D^2 style of test misallocates vertices in the opposite direction to every engine surveyed. Normal maps do not transfer; the Gouraud analogue is to blend the vertex colour with the same factor as the height. Fog/haze is a constant and hides nothing that the morph does not, but it is the cheapest cover for whatever residual popping remains at the far band.

### Gaps
- No source measures how a per-vertex CPU morph interacts with a hard per-vertex cap like 32,767; CDLOD's 4:1 triangle ratio per level is the only stated budget relation.
- The brief's engine specifics (actual split criterion, FOV, frame-to-frame determinism of the rebuild) are not verifiable from any source here and must be measured on the target.
