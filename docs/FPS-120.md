# 120 fps: what caps the sandbox at 60 today, what to change, and what it would and would not buy

*Analysis only, 2026-10-02. Nothing here was run; the sandbox was not touched. Source line numbers for
`music-fix/strlkproxy.c` are those of commit `b026d17` (the working copy carries +4 lines of uncommitted
telemetry edits from line 876 on). The player's question: "what could we do / what would the implications be to get
it up to 120 fps?"*

## The short answer

- **Today's 60 is not the panel and not vsync as configured.** The display is 3440x1440 at 179 Hz
  (`Win32_VideoController.CurrentRefreshRate = 179`, re-measured today). dgVoodoo's `ForceVerticalSync = false`
  (`i76-uncap-lab/game/dgVoodoo.conf` line 90), `FullScreenMode = false` + `FullscreenAttributes = fake` +
  `WindowedAttributes = border` (lines 25, 51, 56: a borderless window, composed by DWM at the desktop's 179 Hz),
  `FPSLimit = 21` in `[GeneralExt]` (line 42) **does not cap this build** (capture 014: "FPSLimit=21 did not cap
  this build (it ran at 60 fps, vsync)"), and the proxy's own cap is off unless `I76_FPS_CAP` is set (TEST-FRAMERATE
  sets it only in `stock20` mode). The music-fix README's phrase "the display's 60 Hz" is wrong on this machine: the
  desktop is 179 Hz.
- **The 60 is an unexplained ceiling that the lab closed as "accepted" on 2026-08-10**
  (`i76-uncap-lab/docs/framerate/README.md` section 6). Every lever tried was inert: FPSLimit 0/21/30/45/90/120
  (even 30 still measured 60.2), a forced "640x480@120" (silently ignored - see below, the syntax was wrong),
  `ForceVerticalSync = false`, the 179 Hz monitor, the NVIDIA profile (user-verified clean), and the zglide
  `grBufferSwap(1)` -> `(0)` byte patch at file offset 0x2303 (60.1, unchanged). The one untested lever is the
  renderer's `grSstWinOpen(..., refresh = GR_REFRESH_60Hz, ...)` request at zglide VA 0x10001D9D.
- **So the plan is: (1) find the ceiling with one 30-second measurement, (2) remove it, (3) pace at 120 with the
  proxy's precise cap** (`I76_FPS_CAP=120`), **with the current switch set unchanged.** The proxy's frame-rate
  machinery is time-based, not frame-count-based, and nothing in it assumes 60 (audit below); the physics stays at
  24 steps/s under `I76_FIXED_STEP=24`, so at 120 fps **four frames in five draw an interpolated pose**. The
  visual gain (motion continuity, panning, free-look) is real; **input latency, AI and physics fidelity do not
  change**, because input is read per frame but only consumed by the 24 Hz step, and because the fixes pin AI and
  per-frame effects to a 20 Hz time grid. Render interpolation also adds its usual one step (41.7 ms) of display
  latency, the same at 60 and 120.

**Two things the record got wrong, which re-open cheap tests:**

1. The forced-refresh test used `640x480@120`. dgVoodoo's documented syntax is `WxH, R` with a comma
   (readme section 7: `"128x128, 60"` forces 60 Hz; `"unforced, 75"` forces 75 Hz at an unforced size), and the
   same readme lists as a known issue that arbitrary refresh overrides do not work *for DirectX emulation* - which
   says nothing about Glide. So `[Glide] Resolution = 3360x2100, 120` has **never been tried**; with the comma it
   is one conf line.
2. `uncap-vsync.ps1`'s header says the swap interval "is the 60fps cap"; the README measured that it is not.
   Whoever extends the script should fix the header.

**The decisive measurement (30 s, no patching):** while the game runs at 60 in a mission, sample the main thread's
EIP with `i76-uncap-lab/tools/instruments/where-spinning.ps1 -Samples 60` (WOW64 context, attributes each sample to
a module). The thread spends about two thirds of each 16.7 ms waiting; the module it waits *in* names the ceiling:
`glide2x.dll` = dgVoodoo's own pacing (refresh emulation or its limiter), `dxgi.dll` / `d3d11.dll` / `nvwgf2um.dll`
= DWM/driver present throttle, `ntdll` under `i76.exe` / `win32.dll` = an exe-side Sleep. Nothing else in the lab
distinguishes these.

**How to remove it, in order of cost (each followed by `probe-loop.ps1 -Fps` or the telemetry dt column):**

1. `[Glide] Resolution = 3360x2100, 120` (and restore). If 120 appears, done: `I76_FPS_CAP=120` then holds it.
2. If not: force the Glide refresh request from the proxy without a code cave. zglide reaches
   `grSstWinOpen` through its own IAT slot (`_grSstWinOpen@28` at 0x10018124, thunk stub 0x10004A4A). The proxy
   already rewrites IAT slots (`strlkproxy.c` 495-520, the `winmm` mci hook) and installs itself before the
   renderer DLL is loaded; a wrapper installed at the first frame-hook call (`GetModuleHandleA("zglide.dll")`,
   rewrite the one slot) that passes every argument through except `refresh = 8` (`GR_REFRESH_120Hz`; 85 Hz is 7)
   is a 20-line opt-in (`I76_GLIDE_REFRESH=120`). Verify the write landed by logging the old pointer and the first
   call's arguments.
3. If the sampler says the wait is in DXGI/driver: `[GeneralExt] PresentationModel = flip_discard` (flip model
   under DWM) and re-measure; then the NVIDIA per-app profile for `i76.exe` (the Global tab was checked, the
   Program tab was not recorded).

With the ceiling gone the game runs unpaced (hundreds of fps in menus is the historical "uncapped"), so the proxy's
cap is mandatory from the first run: `I76_FPS_CAP=120` waits on QPC at the frame-clock call (0x4039B8) and resyncs
when it falls behind (`strlkproxy.c` 876-895).

## 2. Proxy audit: what breaks, and what does not, above 60 fps

Everything the proxy does per frame is driven by the frame's dt or by QPC time, not by a frame count, so there is
no 60 baked in. The sites, each with what happens at 120 fps (8.33 ms frames), the risk, and the fix if one is
needed:

| site (`strlkproxy.c` @ b026d17) | what happens at 120 fps | risk | fix |
|---|---|---|---|
| **Hires clock** `hires_clock_ms` 773-777: integer ms since start replaces GetTickCount at simclock's two call sites | simclock sees dt = 8 or 9 ms; then the frame hook overwrites `dt`/`sim_dt`/`rate` with the exact QPC interval when `sim_dt == dt` (offline) and 0.001 <= dt <= 0.2 s (line 914). 8.33 ms passes both tests. `simclock_time` keeps its own ms sum (unchanged). No floor at 8.33 ms | none up to 1000 fps (dt < 1 ms falls back to integer ms and simclock's own 1 ms clamp) | - |
| **Precise cap** 876-895: `Sleep(left_ms - 2)` then spin | per-frame budget 8.33 ms, so `Sleep(0..6)`. Neither `i76.exe`, `glide2x.dll`, `u32x.dll` nor the proxy calls `timeBeginPeriod` (only `win32.dll` = i76fix does, and that exe lacks the winmm import the proxy needs). On Windows 10 19045 timer resolution is per process, so an un-raised 15.6 ms `Sleep` quantum would make the cap deliver ~60 at a 120 setting | **medium** (the 20 fps cap measured 50.00 ms, sd 0, so *something* in-process - D3D11/driver - already raised it; not proven for all sessions) | add `timeBeginPeriod(1)` in `apply_frame_cap` (one line; `winmm` is already loaded by the proxy); confirm with the dt histogram |
| **20 Hz grid** 921-927: `g_acc20 += dt; tick when >= 0.049; -= 0.05` | a grid frame every 6th frame (6 x 8.33 = 50.0 ms); the 1 ms tolerance still covers float rounding. Everything gated on `g_tick20` (lock tones 985-996, radar ping 1018-1032, flamer ageing/damage 1050-1067, AI fire cache 1083-1101, ammo digits 1107-1109, smoke update 1116-1127, trail fade 1133-1150) keeps its 20 per second | none | - |
| **Per-frame rescaled constants** 918-922: clouds, free-look, zoom, throttle keys = constant x dt x 20 | k = 0.1667 per frame; six calls per 50 ms sum to the stock step. Clouds: the rear mirror redraws every 2nd frame (frame-count, framerate.md row 7), so the main+mirror call ratio stays 1.5/frame and the measured 0.0300 /s invariance holds at any rate | none | - |
| **AI gains** `ai_rate20` / `ai_dt20` 1002-1006 | constants; the 1/dt one-frame gains stay the 20 fps values | none | - |
| **AI fire cache** 1083-1101, keyed on `g_tick20_n` | one decision per 50 ms window, held for 5 intermediate frames instead of 2 | none | - |
| **Fixed-step accumulator** `fixed_stepper_begin` 1475-1484: `acc += sim_dt; n = (int)(acc / step)` | n = 1 on every 5th frame (41.67 / 8.33), n = 0 on four of five (at 60: two of five). The remainder is carried, so the mean stays 24.0 steps/s; the step lands on a 5- or 6-frame cadence as float rounding dictates (same alternation as 60's 2/3). The `n > 20` clamp (1480) only triggers below 1.2 fps | none for physics (it never sees frames); cadence jitter is absorbed by alpha | - |
| **Render interpolation** `ient_update` 1592-1625: `n == 0` keeps `prev`/`prev2`, `alpha = acc / step` clamped to [0, 1] | alpha advances in steps of 0.2 over four interpolated frames; at the frame before a late step alpha sits at ~1.0 (draws the current pose) and the step frame restarts at ~0.2 - continuous, as at 60. Slot reuse after 60 stale *frames* (1600) = 0.5 s at 120 instead of 1 s - still far longer than a vehicle is ever untouched. Teleport guard is distance-based (1622) | none | - |
| **B-spline for world cameras** `xf_bspline` 1559-1572 (`I76_INTERP_SMOOTH` 1 = world cameras) | half a step (20.8 ms) behind, same as at 60; smoother because more samples per step | none | - |
| **Camera hooks** `cam_update_wrap` / `render_wrap` 1703-1800: the frame loop's camera update and the 6 FSM camera actions run on drawn poses | per frame as now; the chase camera's own lag is dt-based | none | - |
| **Engine dt fix** `engine_substep_dt` 831-840 | returns the stock 0.05 whenever the fixed step is on | none | - |
| **Smoke extrapolation** 1116-1127: `t = g_acc20 - 0.05` in [-0.05, 0] | five extrapolated draws per grid window instead of two; `renderer_QueueSmokePuff` called per puff per frame | none (cost only) | - |
| **Telemetry** `tel_frame` from the frame hook (878): one 628-byte datagram + shm write per frame | 120 datagrams/s (75 KB/s); `step_count` reads 0 on four frames in five | low: the consumers. `tools/ffb/FfbMixer.ps1` runs its own loop (~62 Hz, its NYQUIST note) and reads the latest frame, so it does not care; `i76tel.py --csv` doubles its rows | none required; note it in the telemetry README |
| **Music proxy status poll** (0x424550, every 5 s on game time; `strlkproxy.c` 165-171) | unchanged | none | - |
| **Crash logger**, **far clip** (`I76_FAR_CLIP`, 1800 in `-Mode all`) | per frame as now; the draw work at 1800 m runs twice as often | **medium** as a *headroom* question: if the engine cannot finish a frame in 8.3 ms the rate floats below 120 and `I76_FPS_CAP` is moot (interpolation copes with variable dt) | measure the uncapped frame time first (section 5, step 2) |
| `I76_FPS_CAP` parse 953: 5..1000 | 120 accepted | - | - |

**The "per-frame tick delta / 4 floors to 0 above 45.5 fps" item** in `docs/FRAMERATE-UNCAP-RESEARCH.md`
(route 3, line ~107) is **anpage's MechWarrior 2 jump-jet bug, not an I'76 site**. I'76's simclock keeps time as
float seconds (`subsystems/simclock.md`), the stepper is `floor(dt x 20) + 1`, and no integer-ms division of dt was
found in the frame loop or the substep tree (framerate.md "the static screen is exhausted"). Under the hires clock
the only integer path left is the ms counter the frame hook overrides (line 914). Nothing floors at 8.33 ms.

## 4. Implications per subsystem

| subsystem | at 120 fps with the current switch set | changes vs 60? |
|---|---|---|
| Physics (`I76_FIXED_STEP=24`) | 24 steps/s, 41.7 ms each, unchanged: jumps, coasting loss, body rest fraction all follow steps/s (capture 014 "step rate is the physics' real clock") | **no** |
| Render | every frame drawn; 4 of 5 interpolated (`I76_RENDER_INTERP`); motionless-frame fraction should read 0.00 as at 60 | smoother; the 60 fps "still 0.31-0.33 -> 0.00" result should hold |
| Input | sampled per frame (8.3 ms) but consumed by the next physics step; the step's position in the frame sequence is what sets latency: mean half a step (~21 ms) plus the interpolation's one-step display lag | **no** (the extra 4 ms of sampling granularity is below the step quantum) |
| AI | throttle/steer gains pinned to 20 fps values; fire decisions on the 20 Hz grid; `ai_FrameTick` runs per frame with dt | no measurable change expected (same mechanism that held at 60, n = 3) |
| Script VM | one pass per frame; time waits on the mission clock | neutral by audit |
| Sound | per-frame sound starts gated to 20 Hz; loops keep their keep-alive | no |
| Camera | free-look/zoom dt-scaled; chase and cockpit dt-based; death/orbit/head-look steps per frame (section 3) | the unfixed camera keys get 2x faster |
| Telemetry / FFB / motion | 120 frames/s published; consumers poll the latest | no (document the rate) |
| CPU/GPU | the whole loop runs twice as often; REALTIME_PRIORITY_CLASS is raised and dropped around every render (0x403e47) - 240 priority flips/s | headroom must be measured; with `I76_FAR_CLIP=1800` the draw cost is the likely limit |
| Saves, music, label table, health % | not per-frame | no |

## 6. Sandbox test protocol (for the integrator)

All in `C:\Users\james\i76-uncap-lab`, at the physical console (not RDP), with no other i76 process and the
`.console-test.lock` free. Never the portable install.

**0. Baseline, unchanged config.** `TEST-FRAMERATE.ps1 -Mode all -Mission t02` (sets `I76_HIRES_CLOCK=1
I76_FIXED_STEP=24 I76_FRAMERATE_FIXES=1 I76_ENGINE_DT_FIX=1 I76_RENDER_INTERP=1 I76_FIX_HEALTH_PCT=1
I76_FIX_LABEL_TABLE=1 I76_FAR_CLIP=1800 I76_TELEMETRY=1`). In a second shell: `python tools\telemetry\i76tel.py
--csv base60.csv` (from i76-everywhere). Expect `dt` 16.6-16.8 ms. While it runs: `tools\instruments\where-spinning.ps1
-Samples 60` - record the module split. This is the answer to "what caps it".

**1. Lift the ceiling, one change at a time, restoring after each.** Back up `game\dgVoodoo.conf` to
`dgVoodoo.conf.pre-120` first.
   - a. `[Glide] Resolution = 3360x2100, 120` (comma syntax). Boot, `tools\framerate\probe-loop.ps1 -Fps` or the
     telemetry dt. If 120-179 appears, go to step 2. Restore the line.
   - b. If (a) fails and the sampler said `glide2x.dll`: build the `I76_GLIDE_REFRESH=120` IAT wrapper (section 1,
     item 2); log old pointer + first-call args; re-measure.
   - c. If the sampler said DXGI/driver: `[GeneralExt] PresentationModel = flip_discard`; then the NVIDIA Program
     tab for `i76.exe`. Restore.
   - Do not leave `uncap-vsync.ps1`'s patch applied; it is proven inert and the `.orig` restore path needs the game
     closed.

**2. Pace it.** With the ceiling gone, add `I76_FPS_CAP=120` to the `-Mode all` set (TEST-FRAMERATE.ps1 clears it
unless `stock20`; add a `-Cap` parameter or export it by hand before the script). Record `cap120.csv`.
   - **Frame dt histogram:** `dt` column of the telemetry CSV (or `fr_probe.py --tag ... --fps 120 --interp` then
     `analyze.py`, which prints the top `simclock_dt` values). Pass: mean 8.33 ms, sd < 0.5 ms, no 16-17 ms mode.
     A bimodal 8/16 histogram = the `Sleep` quantum; add `timeBeginPeriod(1)` and repeat.
   - **Headroom:** one run with `I76_FPS_CAP` unset (pure uncapped) - the mean dt is the engine's frame cost. If it
     is above 8.3 ms, the 120 target is not reachable with the current render settings; note it and test at the
     rate it does reach.
   - **Motionless-frame %:** `fr_probe.py --interp` + `interp.py <tag>`: `still true` should be ~0.80 (4 of 5
     frames without a step), `still drawn` 0.00, `rough drawn` <= 0.06 as at 60 (capture 014: 0.04-0.06).
   - **Step rate:** telemetry `step_count` summed over a second = 24 +- 1.

**3. The jump.** Same ramps and script as capture 014: `fr_probe.py --tag j120 --fps 120 --fixed 24 --frfix
--enginefix --hires --interp --mission t06.msn --place 7930,<y>,42580,28,<ramp>` then `python jump.py j120`,
beside a fresh `jump f24 at 60` control run the same day (same-rate control rule: two runs per condition, report
n). Pass: speed at foot, apex y/z and the came-down z within the 60 fps spread (capture 014: 26.0-26.7 m/s, apex
25.7-25.9 at z 42765, down at 42797-42800). For the canonical Mission 5 canyon jump use
`autotest\enter-mission5.ps1` (needs save002) and `tools\framerate\physics-trace.ps1 -Profile jump` at 60 and 120,
then `trace-diff.py`; fall speed and airtime must match at equal elapsed time.

**4. Collision.** `tools\framerate\cactus-ab.ps1 -Rates 60,120 -Runs 3` (its `Set-Rate` must learn to export
`I76_FPS_CAP` instead of toggling `I76PATCH.DLL`). Hit rate at 15 m/s should match 60's 67% within the binomial
spread; a drop is the sweep/step mismatch and is reported, not fixed here.

**5. Crash watch.** `game\mciproxy.log` after every run: `fps-cap: 120 fps`, `hires-clock: 2/2`, `fixed-step:
24.00`, `framerate-fixes: 36/36`, `render-interp: 11/11`, and no `crash:` block. A 10-minute free drive in t02 with
hood view (F6) and binoculars, since those are the far-clip crash paths (FARCLIP-CAMERA-CRASH.md).

**6. Human pass** (James, console): chase and cockpit smoothness, free-look, the lock tone (should still be 20/s),
sky speed, the Mission 6 ramps. Record verdicts in i76-map `captures/014-framerate/README.md` next to the 60 fps
ones.

**Restore:** `dgVoodoo.conf.pre-120` back, env vars cleared, `TEST-FRAMERATE.ps1` restores `STRLKUP.DLL` itself.

## Measured 2026-10-02 (after the analysis above)

The ceiling was **hole 2**: ZGLIDE.DLL's `grSstWinOpen(..., GR_REFRESH_60Hz, ...)`. dgVoodoo paces windowed presents
at the refresh the app asked for, so the panel (179 Hz), `FPSLimit`, `ForceVerticalSync=false` and a forced
`[Glide] Resolution = 3360x2100, 120` (tried today: still 60.0) do not matter. The proxy now carries
`I76_GLIDE_REFRESH=<hz>`: a `LoadLibraryA` hook catches ZGLIDE.DLL loading and repoints its
`glide2x.dll!_grSstWinOpen@28` import slot at a wrapper that substitutes the refresh code (120 = 8). No code cave
needed. Sampler before the fix: main thread 14/23 samples in an ntdll wait reached from `nvwgf2um.dll` (the NVIDIA
D3D11 user-mode driver's present), i.e. waiting on the swap, not computing.

`tools/telemetry/frame_stats.py` over the "all" switch set on t01, n = 1 run per rate, same session:

| | 60 (stock request) | 120 (`I76_GLIDE_REFRESH=120`) |
|---|---|---|
| frames/s, driving | 60.0 | 120.1 |
| frame dt mean / sd / p99 (ms) | 16.68 / 0.21 / 17.12 | 8.34 / 0.06 / 8.45 |
| physics substeps / s | 24.0 | 24.0 |
| hood view (F6), binoculars (B) at 1800 m far clip | 60.2, no crash | 120.2, no crash |
| frames whose *physics* pose did not change | 60 % (24 of 60 frames step) | 80 % (24 of 120 step) |

The last row is the physics pose that telemetry snapshots, not the drawn pose: with `I76_RENDER_INTERP` every frame
draws an interpolated pose, so it says how much work the interpolation does (4 of 5 frames at 120), not that the
picture stutters. The drawn-pose roughness measurement (`interp.py`, capture 014) has not been repeated at 120 yet.
Not yet measured at 120: the Mission 5 jump, the collision sweep (`cactus-ab.ps1`), a human pass. The cap
(`I76_FPS_CAP`) was not needed: the refresh request alone paces the game.

## Above 120 (2026-10-02, late): not through the Glide refresh code

Asked for 180 on the 179 Hz panel. Measured on the sandbox, `frame_stats.py`, n = 1 each: `I76_GLIDE_REFRESH=0`
(GR_REFRESH_NONE, code 0xff) -> 60.0 fps; `=100` -> 100.1 (dt 10.00 ms, sd 0.08); `=90` -> 90.1. So dgVoodoo paces
strictly by the code. Raw codes above the Glide 2.x table (probe knob `I76_GLIDE_REFRESH_CODE`): code 9 ->
`grSstWinOpen` returns context 0 and the exe faults at 0x42e209. The wrapper now reopens with the renderer's own
refresh when a code is rejected. 120 Hz (code 8) is therefore the ceiling of this route; anything higher needs a
different lever (frame generation on top of 120, or a Glide wrapper that paces by the desktop refresh).
