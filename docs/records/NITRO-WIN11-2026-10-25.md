# Nitro on Windows 11 (the October 2026 update): first-frame fault, 2026-10-25 (nitro-win11 lane)

The problem: NITRO-PARITY-2026-10-24 s.3/s.5 found that Nitro faults at the first frame on the laptop bench (Windows 11, this week's
cumulative update), with the owner's proxy too. Gold runs there with dgVoodoo 2.87.5 plus the winmm heap fix.

**Result: our Nitro copies still carried dgVoodoo 2.87.3, and the fault is 2.87.3's DirectDraw start-up crash, the same one Gold had
(LAPTOP-BENCH-2026-10-24 s.4, DGVOODOO-UPDATE-2026-10-24).** Neither the proxy nor the game causes it. The fix is the dgVoodoo 2.87.5 x86 set
that the Gold release candidate already uses. It needs no proxy change and no conf change. It is installed in main Nitro. The Nitro LAN pack,
the lab Nitro tiers and `tools\Build-From-GOG.ps1` still carry or download 2.87.3 (s.5).

  28b8ae27) without logs. **Its dgVoodoo is 2.87.3** (DDraw ab19386d, Glide2x 8af442bc). The parity lane's `parity-nitro` copy had the same.

  - This is byte for byte the Gold signature (LAPTOP-BENCH s.4: `DDRAW.dll+0x4AB0A`, read of 0, frame 0 state 5, after grSstWinOpen).
- **Plain GOG Nitro** (`<re-archive>\sandbox-gog\nitro-full\app`: OpenGLide glide2x c319a4f3, the system ddraw, no proxy), `nitro.exe -glide`

## 2. Diagnosis

- The module is dgVoodoo's **DDraw.dll**, not Glide2x or D3DImm. On Nitro, ZGLIDE's start-up goes through DirectDraw, which is why the fault
  follows `grSstWinOpen` even on the Glide path.
- `DirectDrawCreate(NULL)` from a bare 32-bit process (`tools\ddraw-probe.ps1`):
  - In session 1 (DGVOODOO-UPDATE s.2): 2.87.3 raises an access violation and 2.87.5 returns hr=0.
  - **In session 0 (ssh), 2.87.5 also raises an access violation** (new today, n 1). The system ddraw returns hr=0 there. A session-0
    probe is therefore no test of a dgVoodoo version; use the interactive session.
- 2.87.4's release note ("Fixed the crash with Win11 26H1+ builds") is the fix. The proxy's keys (TMUFIX, GLIDE_REFRESH, aspect,
  cursor map) were not bisected. The crash goes away with the DLL alone, and every key stays on in the passing runs below.
- The proxy works the same under 2.87.5 on Nitro: `cursor-map: dgVoodoo ddraw.dll: 2 cursor pointer(s) taken`,
  `zglide-tmufix: ZGLIDE+0x2c9a 75 26 -> eb 26`, and the aspect sites 20/20. These are the same lines as under 2.87.3.

## 5. For main (not done by this lane)

- **Every Nitro deliverable needs the same seven files** (source `<archive>\dgvoodoo\2.87.5\x`, `MS\x86` + `3Dfx\x86`):
  - the Nitro LAN pack;
  - the Nitro kit;
  - the Macs' Nitro, if it uses dgVoodoo rather than DxWnd + OpenGLide (Wine does not take the Windows update, so this is consistency only);
  - lab `test-nitro` / `dev-nitro` (both still ab19386d).
- **`tools\Build-From-GOG.ps1` still downloads dgVoodoo 2.87.3** (lines 48-54) and passes it as `-DgVoodooDir` to
  `package-patch-kit.ps1`, which has since moved to 2.87.5. package-patch-kit now expects 2.87.5 there and a mandatory
  `-DgVoodooFallbackDir` (2.87.3). So Build-From-GOG is out of step: it either fails the md5 check or, if it were patched only to get past
  the check, it would ship 2.87.3 to a Windows 11 user. It should download `dgVoodoo2_87_5.zip` (sha256 5ffde692...40850, DGVOODOO-UPDATE s.5)
  and 2.87.3 as the fallback. Not run or changed here.
- If useful, the proxy could recognise this signature (fault in DDRAW.dll at +0x4AB0A with frame 0) and show "update dgVoodoo to 2.87.5"
  instead of "Unhandled Exception". This is not built.
