## 2. Three proxy fixes the Macs needed (ad904941 = HEAD 3f3882c music-fix + this lane's diff; MSVC /Brepro, built 3 x identical)

1. **Exe detection under DxWnd.** e4005491 on the laptop logged `exe: nitro stamp, unknown .text` and took the Gold path:
   cam-ground, hull, hires clock, frame hook, health and label table were all "bytes differ" (`mciproxy.dxwnd-run1.log`).
   A direct `wine nitro.exe` start of the same folder logged `exe: nitro 28b8ae27`. The cause is DxWnd's injection, which
   has changed 4 bytes of .text (first at 0x4BFC80, the CRT entry) by the time DllMain runs. Fix (nitro.c): if the
   in-memory crc fails, compute the crc of .text from the exe file. If that matches, the exe is Nitro and the differing bytes
   are logged. Each site keeps its own signature check against memory. On the Macs: `exe: nitro 28b8ae27 (file .text
   matches; 4 byte(s) differ in memory, first at 0x4BFC80 ...)`, `429 code sites, 429 match memory` (every boot, 3 Macs).
2. **The PIT probe is fatal under Wine.** `wine: Unhandled privileged instruction at address 0049ACB7` started winedbg and
   showed a "Program Error" box (laptop, n 2: under DxWnd and direct). The July Mac notes (setup-nitro.sh) had the same crash
   and fixed it with AiO's patched nitro.exe, but our proxy needs the stock exe. Fix: `I76_NITRO_PIT_SKIP`, Nitro only,
   default 1 when ntdll exports `wine_get_version` and 0 on Windows (the PC path is unchanged). It turns 0x49acb7 (`cli; mov
   al,0xb8; out 0x43,al`, checked) into `jmp 0x49ad00`, the probe's own failure exit. The caller then stores 200 MHz. Log:
   `pit-skip: on, read back OK` (every Mac boot).
3. **NITSHELL / ZGLIDE never seen.** DxWnd takes nitro.exe's LoadLibraryA slot after DllMain. This is the problem mpmenu.c
   solved for Gold ("TWO WAYS IN"). The result was no ARENA+ shell hooks and no ZGLIDE TMU fix (`zglide-tmufix: armed` and
   nothing after, laptop). Fix (strlkproxy.c): `nitro_shell_watch` polls both modules. Once a module has been resident for
   750 ms and the hook has not attached it, the thread attaches it through hook_LoadLibraryA's own path. Each attach runs
   once (interlocked). On the Macs, every boot logged `NITSHELL.DLL resident ... attaching from the watch thread`,
   `nitro-mp: nitshell hooks: dpEnumSessions ok (... 604 + 7676), dpOpen ok`, `nitro-form: ON - 6/6`, and
   `zglide-tmufix: ZGLIDE+0x2c9a 75 26 -> eb 26`.

Not run: a PC smoke of ad904941. On Windows, the detection fallback is reached only when the in-memory crc fails, the PIT skip
defaults to off, and the watch thread finds the hook already done. The Gold path is not touched: exe_detect's change sits
inside the Nitro stamp branch. A Gold / Nitro PC smoke is owed before this build goes into any PC pack.

## 8. The launch stubs see only their own app's processes (2026-10-22 draft; corrected and tested 2026-10-23 night, nitro-mp-design lane)

**The bug (all four stubs: i76-launch-stub, i76-nitro-app-stub, i76-nitro-stub, i76-settings-stub).** They recognised "their"
game and windows by name or path across the whole Mac: pgrep of `i76.exe` / `nitro.exe` / a Windows exe path, and every large
window owned by any process called "wine". Wine rewrites each Windows process's argv to its Windows command line
(`nitro.exe -glide`, no path), so:
- the Nitro app's stub looked for `C:\GOG Games\Interstate 76 Nitro\nitro.exe`, never saw its own game, left its boot loop after
  120 s as "not booted" and reaped: an unattended Nitro game died at about 140-180 s (the MP lane's joiners at 150-180 s; their
  runner paused the stub with SIGSTOP as a workaround);
- the reaps ran `pkill -9` on Windows paths and on dxwnd.exe / AutoHotkey: quitting one app killed the other apps' games
  (every Nitro app's nitro.exe; from Gold, every app's dxwnd.exe and AutoHotkey);
- the quit detection (render window closes, count of large windows drops to 1) counted every app's windows.

**First fix (2026-10-22, uncommitted draft): own = WINEPREFIX in `ps -E`.** It does not work. On a live boot of a clone
(laptop, 2026-10-23 21:15) `ps -E -p <nitro.exe>` printed only `nitro.exe -glide`: Wine's argv rewrite also overwrites the
environment block that ps reads. Only wineserver still showed WINEPREFIX. So that draft had the old boot-loop bug exactly. That
build (016556bf) had already been put into the laptop's shipped Nitro app on 2026-10-22 13:02; it is replaced below.

**The fix as committed: own = the executable image.** Every app (Gold, Nitro, each lab clone) carries its own copy of Wine,
and every Wine process of that app runs `<bundle>/Contents/SharedSupport/wine/bin/wine` (or `.../wineserver`), which
`proc_pidpath` reports whatever argv says (`tools/nitro-mac/pidpath.swift`, run on the live clone: nitro.exe, dxwnd.exe,
explorer.exe, services, winedevice, rpcss, all under the clone's bundle). `ownProcs(A + "/Contents/SharedSupport/")` lists
those; the game check (`nitro.exe` / `i76.exe` in the command line of an own process), the window count (CGWindowList owner pid
in that set) and the final kill (SIGKILL to that set, after this prefix's `wineserver -k`) use only them. Builds (laptop,
`swiftc -O -target arm64-apple-macos11.0`, `~/i76-nitro-mac-20261021/stub3/`): nitro-app **e7bbd4fc**, launch (Gold) 88934d55,
nitro (DxWnd satellite) 5d8d50d7, settings dedca441.
