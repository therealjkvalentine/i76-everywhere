## 1. The join

**Proxy md5s (check-which-build-is-live).** PC main Nitro: proxy 3f27c797, nitshell a32ffba6, IPXWrapper b8464944 (instance N,

**The owner's session (logs left in both folders, 2026-10-25 20:12-20:21).** PC: hosted `Desert Sun` (species 7676, Arena Drop-In + AI) and broadcast it every 1-4 s;
from the Mac only two 4-byte broadcasts, one per Mac boot, no unicast. Mac: listed `ARENA+ Desert Sun`,
`dpOpen ... -> 0`, then the shell's "Cannot open connection to game", in both boots. The macOS unified log at 20:10 shows the uncap
clone (deleted at its lane's end) uninstalled and its UUIDs removed, at 20:12:34 `LocalNetwork: found bundle id
com.i76everywhere.test.i76.nitro.sky.lab by UUID 03B81E57-...`. The Local Network rules (`/Library/Preferences/
com.apple.networkextension.plist`) hold `com.sikarugir.Interstate76Nitro` as **allowed** (multicast preference set, not denied) and
no rule for the lab clones. LaunchServices held 4 records with the launcher's UUID (the app, the Relay Lab, two MP Lab copies in the
Trash) plus a Sky Lab one.

**How it got repaired, and the rule.** Starting this lane's test clone (same bundle id as the app) made macOS log "apps installed
com.sikarugir.Interstate76Nitro ... Populating the cache with 1 UUID(s)", and the cache entry turned from 135ba2b6 to 03b81e57.
So the repair is a re-registration of the app; the deploy does it explicitly (`lsregister -f`) after unregistering the stale lab
records, and the cache was read back afterwards. The old rule "keep the UUID and the Allow carries over" (NITRO-MAC s.8,
build-stubs.sh) is right but not sufficient: **after replacing a launcher in place, re-register the app**, and **never give a clone
the shipped launcher's UUID** (deleting such a clone fires an "uninstalled" notice that drops the UUID mapping of whatever bundle id it
carried).

## 2. The end menu

The second-level Esc menu ("Abort Mission": Replay / Reconfigure / Abort Mission / Exit Game) in Nitro reads keys from the control
block's first dword at 0x5348f8 (Gold 0x5367c8; Nitro's key step 0x49dfb0 found by aligned bytes against Gold 0x496e10; page pointer
0x5faf80 = Gold 0x654a20, mode 0x503e94 = Gold 0x4fe534). Clicks come through the window procedure (WM_LBUTTONDOWN / UP with mode
0x10 -> 0x4972d0 in Gold); hovering does nothing. In a network game the menu-keys clear zeroed that dword before the menu read it;
57f17f4 fixed that (not in 3f27c797). The owner's Mac case was single player, where that clear does not run.

Lab attempts, all on the PC (private desktop, P01 direct boot): `cellsp.sh` with drv4 (drv3 + `NB_CLICK_STATE=5`: scripted keys and
clicks inside a mission) and `mread.py` (menu mode / page / row from memory). Old proxy under the tick, new proxy under the tick, old
proxy without the tick, and **stock Nitro without any proxy**: Esc opened the menu each time, nothing after it moved the row or the
page. With stock failing the same way, the instrument cannot tell a game fault from its own (keys posted / hooked from a private
desktop do not reach the menu's key path; the clicks' coordinates are not the window's). Network-host attempts with externally posted
messages (`cellm.sh`) did not even open the menu. Next step: run the owner's route on a visible desktop with real input (console
lock), or have the owner try the QA steps below and say which part fails.
