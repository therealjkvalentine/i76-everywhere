# Opentrack CPU / fps cost: what others know, and what to try (2026-10-25)

Context: `docs/records/HEADLOOK-COST-2026-10-25.md` measured about 5-6 fps (~5 %) lost to opentrack tracking on the owner's desktop (i7-7700K 4C/8T). The cost is in opentrack itself (0.6-0.9 of a core), not the head-look layer, and PointTracker costs about the same (camera path, 250 Hz loop). This note collects what is published about that cost and ranks things to try. Search depth: standard WebSearch plus WebFetch of the primary threads; extended for the thin topics. **Evidence is thin and mostly anecdotal; nothing below is a controlled benchmark.**

## The owner's current setup (read from disk, not assumed)
- Opentrack build in `C:\Program Files (x86)\opentrack` (ships `head-pose-0.2/0.4 big/small`, `-int8` / `-f32`, `head-localizer.onnx`; `onnxruntime.dll` 14 MB = the CPU build, no DirectML / CUDA provider shipped).
- `Documents\opentrack-2.3\default.ini` (md5 37206f16...): `[neuralnet-tracker]` has only `camera-name`, `field-of-view=80`, `force-fps=2`, offsets. There is **no `force-resolution`, no thread-count key, no pose-net key**, so the camera runs at whatever resolution opentrack picks by default and the thread count / model are program defaults (unverified which; look in the dialog). `force-fps=2` is an enum index; it is probably "60" (default, 30, 60, 120 is the usual order) - confirm in the dialog before relying on it. There is no `filter-dll` key either, so the filter is the build default.
- Camera: Insta360 Link 2C Pro (UVC, fixed lens, 4K30 / 1080p60 modes; its own AI tracking is a digital reframe).

## Findings
1. **Threads are the best-documented lever.** Issue #1498 (2022): neuralnet sat at ~10 % CPU, then ~80 % with frame-rate problems in DCS; cause: the thread setting had become 16; lowering it fixed it. Issue #1819 (2024, 10-core): CPU ~10 % -> ~70 % and power ~10x when tracking started; a commenter says one thread cut CPU to about a quarter; another says neuralnet is "pretty CPU intensive", PointTracker uses much less CPU and has lower latency, and suggests running opentrack on another PC over UDP. The setting is in the Neuralnet tracker's Tuning/Debug area. Sources: https://github.com/opentrack/opentrack/issues/1498 , https://github.com/opentrack/opentrack/issues/1819
2. **Maintainer's recipe for a game that stutters under neuralnet** (DaWelter, discussion #1859, June 2024): limit threads ("one or two should be fine"), "select a low camera resolution, only 640 px in width or so", select the **small** model via the "Select Pose Net ONNX" button, set Frames Per Second to **30**. The poster also fixed freezes by turning off Windows **Hardware-accelerated GPU scheduling** (a GPU-side stall, not CPU; relevant if the game hitches rather than just averaging lower). Source: https://github.com/opentrack/opentrack/discussions/1859
3. **One inference-time data point**: ~8 ms per frame for head-pose-0.2-big, 2 threads, 720p, 60 fps (Ryzen 5800X3D; discussion #2141). At 60 fps with 2 threads the tracker is busy about half of every 16.7 ms; halving fps halves that. The maintainer there also warns: filter alpha (ROI) 0 is bad, 0.5-0.7 smoothing plus a deadzone is right. Source: https://github.com/opentrack/opentrack/discussions/2141
4. **Resolution**: guides quoting opentrack say to use the lowest resolution that still tracks reliably, because high resolution costs performance; 640x480 / 800x600 at 60 fps is the usual advice. A third-party mirror of the docs (mintlify; **not official, partly inconsistent, treat as unverified**) gives 1 thread ~30-40 fps, 2 ~50-60, 4 ~60-70 and says 320x240 is fastest but misses distant faces. https://mintlify.wiki/opentrack/opentrack/trackers/neuralnet . A release comment (#1853) says the newer pose nets gave higher fps and lower CPU than the old ones; the 64-bit build needs AVX.
5. **Camera decode**: one W3C measurement (different webcams per format, so indicative only) logged MJPEG decode at roughly 2x the CPU of YUY2/NV12 at 720p (68 vs 31 M cycles/s). YUY2 costs USB bandwidth instead (720p30 ~55 MB/s; fine on USB 3, too much for USB 2). The mirror docs list a "Use MJPEG" tickbox (default off). No opentrack-specific measurement found. Our own record says the cost survives swapping to PointTracker, which points at the camera/decode path, so this is a plausible, unmeasured lever. https://lists.w3.org/Archives/Public/public-webrtc-logs/2020Oct/0152.html
6. **AITrack** (separate process: its own ONNX face model, streams 6DoF over UDP to opentrack's "UDP over network" input; can run on another PC; docs say "reasonably low CPU"). No published AITrack vs neuralnet CPU numbers found; a flight-sim user says the AITrack+opentrack combo "costs some FPS" (hearsay). A Condor forum reply says any modern multi-core box can run both. Value is mostly isolation (another core/box), not a cheaper net. https://github.com/AIRLegend/aitrack , https://www.condorsoaring.com/forums/viewtopic.php?p=183536
7. **Phone as tracker** (SmoothTrack and similar apps send head pose over UDP; target port 4242 in opentrack's UDP input): the phone does the vision, the PC only parses packets. Requirements (ARCore-supported Android / ARKit iPhone) and per-app jitter vary; no PC-side CPU figures found. Needs smoothing in opentrack. Moves 100 % of the cost off the PC.
8. **Priority / affinity**: nothing opentrack-specific found. DCS/TrackIR forum users report trying priority classes, realtime, affinity and Process Lasso with no durable fix. Consistent with our n=1 BelowNormal / affinity rows (no benefit beyond noise).
9. **GPU inference**: nothing found; the shipped `onnxruntime.dll` is the plain CPU build and the tracker is described as CPU-only. A DirectML/CUDA opentrack build is a fork-sized job for a net that takes ~8 ms; not worth it.
10. **Insta360 Link 2C Pro**: up to 4K30 / 1080p60. Its AI Tracking (digital reframe) toggles with the camera's Touch Key or the AI Tracking icon in Link Controller; Insta360 lists HDR only up to 1080p30 / 720p30. No source ties it to opentrack. Practical risk: with no `force-resolution` set, opentrack may be opening a 1080p or 4K MJPEG mode, the biggest decode cost of all. The PointTracker profile points at "Insta360 Virtual Camera" (the Link Controller's virtual device, an extra copy hop); the neuralnet profile correctly uses the real device. Do not run both.
11. **250 Hz output loop / Accela**: no source treats these as a CPU cost. Our own measurement (opentrack idle 0.1 % of a core, tracking 60-76 %) says the vision/camera side is the cost, so changing filters will not help.

## Ranked: five things to try tonight (biggest expected gain per effort first)
Dialog path for 1-4: opentrack main window -> **Tracker settings** button (next to the "Neuralnet tracker" dropdown) -> the neuralnet dialog. Stop tracking first. After each change note opentrack's CPU % in Task Manager (Details tab) with a face in view, and play the same hill leg. (Exact tab and label names vary a little between builds; the names below are from the maintainer's posts and the unofficial docs.)

| # | Try | Where | Expected gain | Notes |
|---|---|---|---|---|
| 1 | **Frames per second 60 -> 30** | Camera section: "Frames per second" (we store `force-fps=2`) | Roughly halves tracker work: opentrack ~60 % -> ~30-35 % of a core; most likely 2-4 fps back | 30 Hz pose is fine for I'76 look; the freetrack output still runs 250 Hz. |
| 2 | **Threads -> 1 (or 2)** | Tuning/Debug (or Performance) tab: "Number of threads" | Reports of "a quarter of the CPU" at 1 thread; fewer cores contending with the game's render thread and dgVoodoo | Check the current value first (default unknown; 16 was a real failure case). At 30 fps one thread should keep up. |
| 3 | **Force resolution 640x480 (or 640x360)**, and Link Controller AI Tracking off | Camera section: "Resolution" | Cuts decode + preprocess; possibly the largest hidden cost if it is on 1080p / 4K MJPEG now | Maintainer: 640 px wide is enough. Check the face is still found at the owner's seating distance. |
| 4 | **Small model** | "Select Pose Net ONNX" -> `head-pose-0.4-small-int8.onnx` (already installed) | Less inference per frame | Slightly noisier pose; keep ROI/filter alpha 0.5-0.7 (not 0). |
| 5 | **Take the vision off this PC** | Run opentrack neuralnet or AITrack on the laptop (or a phone app); on the desktop set Tracker = "UDP over network" (port 4242), keep the Freetrack output | Removes nearly all of the 60-76 % core; back to the no-head-look baseline | Needs the camera on the other machine (spare webcam on the laptop, or a phone). Heavier setup; do last. |

If the game hitches rather than just averaging lower: Windows Settings -> System -> Display -> Graphics -> Hardware-accelerated GPU scheduling off (discussion #1859). Defender exclusions remain the biggest single fps-stability lever on this PC (see the record).

## The one experiment to run next in the lab
A **ladder with a real face in view**, same hill route, test-gold, n >= 3 per rung, recording opentrack CPU % and fps with Defender's CPU as a regressor (as before): `b` (current ini) -> `+fps 30` -> `+threads 1` -> `+640x480` -> `+small-int8` (cumulative), with `b_idle` and `a` as bookends. The previous run had nobody in front of the camera (lighter than real use), so feed a face with a looping video through a virtual camera, or seat a person. Rungs are only `default.ini` changes (swap and restore by md5 as before), so `tools/headlook-cost/hlcost-run.ps1` is reused. Success = the rung where opentrack CPU falls below ~25 % of a core and fps returns to the `b_idle` level; ship that profile as the kit's recommended opentrack settings. If rungs 1-4 do not move fps, the cost is not in the vision work and only option 5 (off-box) helps.
