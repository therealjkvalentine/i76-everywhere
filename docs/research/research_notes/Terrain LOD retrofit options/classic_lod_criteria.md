# Classic (1995-2005) heightfield LOD algorithms: split / merge criteria, tolerances, budgets

Scope: Lindstrom et al. 1996, Duchaineau et al. ROAM 1997, Hoppe 1998 (VDPM terrain), Röttger et al. 1998, Pajarola 1998 (restricted quadtree), Ulrich 2000/2002, de Boer 2000 (geomipmapping, the "distance ring per tile" scheme written down), and the TUM terrain-rendering tutorial as a secondary summary. All formulas below were read from the papers' own text (PDFs saved under the session scratchpad `pdfs\` folder, extracted with pdftotext; a few symbols were lost in extraction and are flagged). Nothing here states a value for Interstate '76 beyond what the brief supplied (5 m tiles, ring factors 12.9 / 18.3, floor_pow2(d^2)*B height test, no geomorph, <4 % merges, 32,767 index cap); every I'76-specific number in the Inferences is derived from those givens and marked as such.

Notation used throughout: delta = world-space (vertical) height error introduced by removing a vertex / coarsening a tile; D = eye-to-vertex (or tile) distance; s = tile edge length; tau = screen-space tolerance in pixels; H = viewport height in pixels; phi = vertical field of view; K = H / (2 tan(phi/2)) = "pixels per unit of (error / depth)".

---

## Key question 1: How do the Lindstrom / ROAM / Röttger / Hoppe screen-space criteria relate to "world error / distance" or "/ distance^2", and which is the stock d^2 threshold closest to?

### Takeaway
Every classic screen-space criterion is, to first order, **split when delta / D > tau / K** — the world-space height error divided by the *first* power of distance, scaled by a resolution-and-FOV constant K. None of the surveyed papers uses a distance-squared tolerance; a threshold that grows with d^2 is a different (non-perspective) law that over-details near tiles and under-details far tiles relative to any constant pixel tolerance.

### Cited Findings
- Lindstrom 1996 defines the per-vertex error as "the maximum vertical distance between" the fused triangle and its two sub-triangles ("vertex B's delta value") and projects that vertical "delta segment" onto the projection plane; Eq. (1) gives the projected length as `lambda * d * delta * sqrt((ex-vx)^2+(ey-vy)^2) / ((ex-vx)^2+(ey-vy)^2+(ez-vz)^2)`, where "d [is] the distance from e to the projection plane, and lambda [is] the number of pixels per world coordinate unit in the screen x-y coordinate system". The vertex is removable if this projected length is below the threshold tau; Eq. (2) is the same test squared "so that the square root can be avoided". The paper notes "Whenever ex = vx and ey = vy, i.e. when the viewpoint is directly above or below the delta segment, the projection is zero, and the triangles are coalesced ... less detail is required for a top-down view ... more detail is necessary to accurately retain contours and silhouettes in side views." — [Lindstrom et al. 1996, Sec. 4.1](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- Lindstrom's block (tile) level test: "The discrete level of detail selection is done by computing the maximum delta value, delta_max, of the lowest level vertices for each block. Given the axis-aligned bounding box of a block and delta_max, one can determine, for a given viewpoint, whether any of these vertices have delta values large enough to exceed the threshold tau. If none of them do, a lower resolution model may be used." The block is replaced by four higher-resolution blocks when the largest delta_max of the children exceeds the block's lower bound delta_l (Eqs. 3-4). — [Lindstrom et al. 1996, Sec. 4.2](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- ROAM: each bintree triangle T carries a precomputed nested "wedgie thickness" e_T ("the volume of world space containing points (x, y, z + e_T) ... built bottom-up"); the runtime priority is the "screen-space geometric distortion" obtained "by projecting T's wedgie into screen space ... The bound is defined as the maximum length of the projected thickness segments over all v in T". "The maximum split-queue priority provides an upper bound on maximum distortion." Triangles whose wedgie crosses the near plane get "an artificial maximum" priority. — [Duchaineau et al. 1997, Sec. 6.1-6.2](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Röttger 1998, Eq. (1): "l / d < C for some constant C, where l is the distance to the eye point, and d is the edge length of the block ... C is a configurable quality parameter. The constant C controls the minimum global resolution. As C increases, the total number of vertices per frame grows quadratically." Eq. (2) defines surface roughness `d2 = (1/d) * max_{i=1..6} |dh_i|` (six elevation differences along edges and diagonals), so "the d2-value times d is an upper bound for the error introduced by dropping one level of detail". Eq. (3): decision variable `f = l / (d * C * max(c * d2, 1))`, "subdivide if f < 1"; "C again determines the minimum global resolution, whereas the newly introduced constant c specifies the desired global resolution ... by adjusting c to the current system load, a constant frame rate can be maintained." — [Röttger et al. 1998, Sec. 2.2](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Hoppe 1998 quotes the VDPM refinement criterion from his 1997 paper as mu_v / ||v - e|| compared against a constant "kappa ... [that] accounts for field-of-view angle phi and pixel tolerance tau" (the extracted text shows the factor "2 tan(phi/2)"; the exact placement of tau in the kappa expression was lost in extraction). He then says "The denominator ||v - e|| is an estimate of the z coordinate of the vertex v in screen space. We replace this denominator with the linear functional L(v) = (v - e) . e_hat which computes this z coordinate directly", giving "our new screen-space error criterion is mu_v > kappa * L_{e'}(v)" with e' either the current or the anticipated future viewpoint. The optional sqrt(1 - ((v-e).n/||v-e||)^2) factor "reduces the average number of active faces by only 3%, so we decided to omit it." — [Hoppe 1998, Sec. 4.2](https://hhoppe.com/svdlod.pdf)
- TUM tutorial (tile-based / chunked LOD): "LOD computation is based on the theorem on intersecting lines": epsilon' = epsilon_P * h / (2 tan(phi/2) * P_z), with "epsilon_P: world-space error tolerance at point P; h: viewport height in pixels; phi: fovy; tau: screen-space error tolerance in pixels; P_z: camera-space depth of point P. Use a tile at level l for rendering iff epsilon'/tau <= 1 where P' denotes the point of the tile's bbox with the least depth to the camera." — [Dick/Westermann, TUM terrain tutorial](https://www.cs.cit.tum.de/fileadmin/w00cfj/cg/Research/Tutorials/Terrain.pdf)
- de Boer 2000 (geomipmapping): the switch distance for level n is "D_n = |epsilon| * C" (Eq. 1) with "C = A / T" (1a), "A = n / |t|" (near plane distance over the near-plane top coordinate, 1b) and "T = 2 tau / vres" (1c, vres = vertical screen resolution in pixels). Runtime compares the block-centre distance to the precomputed D_n; "Pre-calculating D_n^2 will reduce the real-time distance ... calculation to d^2 = ...", i.e. the *comparison* is done on squared distances but the *threshold* is linear in epsilon. — [de Boer 2000](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Ulrich 2000 (Soul Ride engine, Gamasutra): vertex test `L1 = max(|vertx-viewx|, |verty-viewy|, |vertz-viewz|); enabled = error * Threshold < L1;` and box test `enabled = maxerror * Threshold < L1` (L1 reduced by the box extents); "for view distance z, the worst tolerated vertex error is roughly z / Threshold"; Threshold is an "adjust-for-best-results slider". — [Ulrich 2000](https://www.gamedeveloper.com/programming/continuous-lod-terrain-meshing-using-adaptive-quadtrees)
- Pajarola 1998 (RQT) uses an object-space error e_T(P) with an absolute tolerance in metres for the triangulation itself; the per-patch LOD is "assigned based on relative distance to viewpoint and view direction" in the scene-management layer. — [Pajarola 1998, Secs. 5, 8](https://www.ifi.uzh.ch/dam/jcr:ffffffff-e53a-93ad-ffff-ffff923549a3/Vis98.pdf)

### Inferences
- Unifying form (my algebra, consistent with all six sources above): pixel error ~= K * delta / D_z with K = H / (2 tan(phi/2)). Lindstrom's `lambda * d` is exactly K (pixels per world unit on a projection plane at distance d); de Boer's C = A/T = (1/tan(phi/2)) * vres/(2 tau) = K / tau; the TUM slide is the same expression written out; Hoppe's kappa plays the role of tau/K; Ulrich's `Threshold` is K/tau with the L1 norm standing in for depth; ROAM's projected wedgie thickness is the same quantity evaluated at the worst vertex of the triangle. Röttger's roughness branch, `l < C * c * max|dh|`, is also delta/l > 1/(C c): linear in distance, with the FOV/resolution constant absorbed into c.
- The flat-terrain branch of Röttger (`l < C * d`) is a pure "distance proportional to tile size" ring; it is the only criterion in the set that splits by tile size instead of by measured error, and the paper keeps it only as a floor ("minimum global resolution") beneath the error-driven branch.
- Lindstrom's full Eq. (1) has the extra factor r / (r^2 + h^2) with r = horizontal distance, h = height difference: for a near-horizontal view (h << r) it reduces to delta/r (linear); only when looking steeply down does the projected error fall faster than 1/D. So the sideways, low-camera view of a driving game is the regime where "error / distance" is the correct law and the 1/D^2 behaviour never applies.
- A tolerance that grows with d^2 (threshold = B * floor_pow2(d^2), i.e. delta_allowed ~= B d^2 within a factor-of-two stair) compared with the perspective law delta_allowed = tau D / K: the two cross at D* = tau / (B K). For D < D* the d^2 law tolerates *less* error than the pixel law (over-detailed, wasted triangles near the car); for D > D* it tolerates more, and the resulting on-screen error grows linearly with distance (pixel error ~= K B D). Far ground is therefore under-detailed relative to a constant-pixel criterion, and the error of each far tile *grows* as it recedes rather than staying constant. Which side of D* the useful range of a 1997 draw distance sits on cannot be stated without the engine's B, which this note does not have.
- The floor_pow2 on d^2 doubles the tolerance every time d grows by sqrt(2) (since 2^floor(2 log2 d) steps at each half-doubling of d). That is itself a set of concentric rings at radii proportional to sqrt(2)^k, independent of the 12.9x / 18.3x tile rings.
- de Boer's "compare d^2 with D_n^2" is a reminder that a squared compare is a cheap implementation of a *linear* threshold; it should not be confused with a tolerance that is itself quadratic in distance. Whether the stock engine's d^2 is a cheap-compare artefact or a genuine quadratic tolerance is for the engine side to establish.

### Gaps
- The exact kappa expression in Hoppe's text was garbled by PDF extraction; the 1997 VDPM paper (SIGGRAPH 97) has it in full and was not fetched.
- Ulrich's 2002 chunked-LOD SIGGRAPH notes PDF uses a custom font encoding and could not be text-extracted; the formula attributed to it here is taken from the TUM tutorial slide that cites it and from the chunklod web page, not from the notes themselves.
- No source was found that uses a distance-squared tolerance, so there is no literature comparison point for the stock engine's law beyond the algebra above.

## Key question 2: Why does a pure distance-ring scheme pop at every ring, and what did the literature say about ring spacing vs continuous criteria?

### Takeaway
A ring scheme splits a tile when it crosses a fixed world-space radius regardless of how much the tile's geometry actually changes, so the pop size is whatever the tile's height error happens to project to at that radius; with tile sizes doubling per level the rings are at powers of two, and de Boer and Röttger both describe this fixed-radius switching as the source of block-LOD popping and introduce geomorphs or error-driven criteria to remove it.

### Cited Findings
- Röttger on earlier block/ring systems: "various real-time simulation systems ... divide height fields into smaller blocks, and generate several multi-resolution triangulations for each of those. Switching between these different levels of detail is done depending on system stress and distance to the point of view ... popping must be handled when replacing a block with one from another level of detail. The visual appearance of the popping effect can be eliminated by geomorphing between both levels of detail. However, this multi-resolution strategy is not optimal, since it is assumed that the distance to the point of view is constant throughout each block." — [Röttger et al. 1998, Sec. 1](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Röttger on Lindstrom's continuous criterion: "With the viewpoint moving, the triangulation is continuously changing, resulting in a phenomenon called vertex popping. As the observer approaches an area with detail information, this detail will suddenly appear at a certain distance." — [Röttger et al. 1998, Abstract](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- de Boer: "When looking at ordinary texture mipmapping, one can clearly see the borders of where two mipmaps of different levels touch each other. These borders ... occur at fixed distances from the camera and can be eliminated by using Trilinear filtering ... This same principle can be applied to GeoMipMaps." And in the conclusion: "The noticeable popping artifacts - which is the nature of block-based LoD methods - has been reduced by using screen-space pixel errors, and can be totally eliminated using the trilinear 'morphing' method I described." — [de Boer 2000, Secs. 3.1, 5](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- de Boer's switch distance is proportional to the block's *measured* error, not its size: "D_n = |epsilon| * C" where epsilon is the block level's maximum vertex height change (Fig. 3: "the geometric height-change which will occur when removing the white vertex ... By taking the resulting max{epsilon_0..n-1} ... we have covered the worst-case scenario"). — [de Boer 2000, Sec. 2.3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Röttger's quadtree halves the block edge per level (height field 2^n+1 square) and the ring criterion l < C d therefore places ring radii at C times each power-of-two block size; the level difference between neighbours is held to <= 1 by propagating d2 values up the tree with factor "K = C / (2 (C - 1)) (C > 2)" (Eq. 5). — [Röttger et al. 1998, Sec. 2.2](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Pajarola: adjacent restricted-quadtree blocks "differ by at most one level in the quadtree hierarchy" to avoid cracks ([17] = Lindstrom). — [Pajarola 1998, Sec. 3](https://www.ifi.uzh.ch/dam/jcr:ffffffff-e53a-93ad-ffff-ffff923549a3/Vis98.pdf)
- Lindstrom argues for continuous (per-vertex) rather than per-block LOD with numbers: the ratio of polygons after block-only selection to polygons after per-vertex selection, n1/n2, "varies between 1.85 and 160" for tau from 0 to 8 px, "which clearly demonstrates the advantage of refining each uniform level of detail block." — [Lindstrom et al. 1996, Sec. 7](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- vterrain.org's survey characterises Röttger 1998 as "very similar to Lindstrom-Koller '96, cleaned up a little and fleshed out, and made unambiguously top-down" and notes geometry clipmaps (2004) "simplifies purely on distance, so it doesn't fit high-contrast terrain well, but polygon count can be pushed so high on modern hardware that it doesn't visually matter." — [vterrain.org LOD papers](http://vterrain.org/LOD/Papers/)

### Inferences
- Pop size at a ring: when a tile of size s splits at radius R = C s, the vertex it introduces moves on screen by about K * delta_tile / (C s) pixels (delta_tile = that tile's true height error). Because delta_tile is uncorrelated with s, a ring scheme produces pops that are small on flat tiles and large on rough tiles at the *same* ring; an error-driven criterion instead splits rough tiles earlier so every pop is about tau pixels. This is the mechanism behind Röttger's "detail will suddenly appear at a certain distance" and de Boer's "fixed distances from the camera".
- With the brief's 5 m base tile and 12.9x factor, the rings sit at 64.5 m (5 m -> 2.5 m children), 129 m, 258 m, 516 m, 1032 m ... (powers of two); the steep variant at 91.5 m, 183 m, 366 m .... A car driving at constant speed crosses the inner rings most often, and every tile on a ring pops at the same moment the camera crosses it, so pops cluster in bands rather than scattering.
- Since Röttger holds neighbours within one level, and the stock engine (per the brief) also rebuilds a quadtree every frame, a single ring crossing can force the neighbour level-balance split as well — one crossing, several pops. The literature's answer is that balance is a crack-prevention rule, not a visual-quality rule, and the visual rule has to be a separate error tolerance.

### Gaps
- No 1990s game postmortem was found that documents its ring factors; the only numeric game-era data are de Boer's (2000) and Ulrich's (2000) article values. Which titles (MechWarrior 2 family, Magic Carpet, Terminal Velocity, etc.) used ring tables remains unsourced here.

## Key question 3: Would a coarser setting, or a fixed level beyond some distance, reduce visible change or just move it? What did the papers measure?

### Takeaway
The papers measured triangles and screen error as functions of the pixel tolerance, and popping as a function of tolerance: a coarser tolerance cuts triangle count steeply (Lindstrom: 2x at tau=0 to >6000x at tau=8) but makes each remaining transition larger; popping is removed by small tolerance (about 1 px) or by geomorphing, never by coarsening alone.

### Cited Findings
- Lindstrom, Hunter-Liggett view at 1024x768: "n0 = 13 x 10^6 ... total number of polygons in the view frustum"; "The ratio n0/n2 ranges from about 2 (tau = 0) to over 6,000 (tau = 8)"; at tau = 1 "n0(1)/n2(1) is slightly above 200, while n1(1)/n2(1) is 18"; "We pay special attention to the data obtained at tau = 1, as this threshold is small enough that virtually no popping can be seen in animated sequences ... seemingly identical to the ones obtained with no mesh simplification"; "threshold of one pixel, even when the surface complexity is reduced by a factor of 200." — [Lindstrom et al. 1996, Sec. 7](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- Lindstrom Table 1 (screen-space displacement in pixels after simplification; columns reconstructed from extracted text, rows tau = 0, 0.125, 0.25, 0.5, 1, 2, 4, 8): mean 0.00 / 0.03 / 0.06 / 0.11 / 0.21 / 0.42 / 0.88 / 1.38; max 0.00 / 0.52 / 0.85 / 1.56 / 2.88 / 5.37 / 10.41 / 16.69; fraction exceeding tau 0 / 6.41 / 4.52 / 3.14 / 2.61 / 2.84 / 3.27 / 1.38 %. "In all cases, the average pixel error is well below tau ... the fraction of displacements that exceed tau is typically less than five percent." — [Lindstrom et al. 1996, Table 1](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- ROAM, fighter-style flight 300 m above the Jemez mountains on 90 m USGS DEM: "with 3000 terrain triangles in the mesh, silhouettes appear realistically complex and stable and there are virtually no popping artifacts. In a similar flight over less rough but still mountainous terrain 1500 triangles suffice to eliminate perceptible popping." Pop histogram "for a 1000 x 1000 image with 3000 triangles per frame": "On average, only 43.2 splits and merges are performed per frame ... less than 3% of the triangles change, and these few, scattered pops almost all measure under 1.5 mm on a typical 21 inch workstation monitor." Histogram axis spans 0-10 pixels. — [Duchaineau et al. 1997, Sec. 8](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Hoppe: "Popping is avoided if the screen-space error tolerance is kept near a value of 1 pixel, but with a constant error tolerance, the number of active faces can vary greatly"; with geomorphs "we can increase the pixel error tolerance to improve frame rate (up to 72 frames/sec) with few noticeable artifacts"; "Even though geomorphs hide such pops, it is still useful to have an accurate estimate of screen-space error." — [Hoppe 1998, Secs. 4.2, 5](https://hhoppe.com/svdlod.pdf)
- de Boer: "Although using screen-space pixel errors to select GeoMipMap levels will deliver a tremendous decrease in popping artifacts, there will still be some occasional popping, especially when tau is set to a high value. Although setting tau to 1 or less will eliminate popping altogether, it also implies that the probability of using a higher level GeoMipMap (lower detail) will be very low. A certain value of tau has to be found which gives a good balance ... This value is unique for every application." — [de Boer 2000, Sec. 3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Pajarola, object-space tolerance vs retained points (Table 1, 25,921-point patches): Albis 1 m -> 76 %, 2 m -> 45 %, 5 m -> 18 %, 10 m -> 7 %; Matterhorn 1 m -> 87 %, 2 m -> 66 %, 5 m -> 40 %, 10 m -> 25 %; "the visual fidelity of a moderate error tolerance of 5 meters ... is still extremely good"; frame rates on an Indigo2 High Impact R10000, 52 km x 52 km hilly scene: full resolution 86,000 triangles at 20 fps, culled 20,000 at 21 fps, adaptive RQT 8,000 at 38 fps. — [Pajarola 1998, Tables 1-2](https://www.ifi.uzh.ch/dam/jcr:ffffffff-e53a-93ad-ffff-ffff923549a3/Vis98.pdf)
- ROAM lists "Atmospheric obscurance: Wedgie priorities can be decreased when fog reduces visibility" among compatible metric variations, and "View frustum: Wedgies outside the six clipping planes can be given minimum priority." — [Duchaineau et al. 1997, Sec. 6.4](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Röttger regulated c (not C) to hold frame rate: "The quality control C was set to a value of 8 ... The value of c was dynamically chosen as to maintain a fixed frame rate of 25 Hertz, which resulted in approximately 1600 triangle fans, or a total of roughly 15000 vertices per frame"; the paper's Figs. 17-19 show the triangulation at 25, 38 and 76 Hz. — [Röttger et al. 1998, Sec. 3](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)

### Inferences
- For a ring scheme the per-pop screen displacement scales as K * delta_tile / (C s): lowering C (coarser rings, nearer to the camera) makes every pop proportionally bigger and the pops happen nearer, where they are more noticeable; raising C makes pops smaller and more numerous and costs triangles quadratically (Röttger: vertex count grows with C^2). Coarsening therefore trades fewer, larger pops for more, smaller ones — it moves the change, it does not remove it. Only tying the ring radius to delta_tile (de Boer's D_n = epsilon C) or geomorphing changes the character of the pops.
- A fixed detail level beyond a cutoff distance R_c removes all split/merge events beyond R_c (no criterion is evaluated there) at the price of a constant residual error that is largest exactly where silhouettes form (Lindstrom and Röttger both note side-view silhouettes are the quality-critical case; Röttger: "The image quality is worst at the silhouettes"). ROAM's fog priority is the literature's version of this: let visibility, not distance, decide how much far error is tolerable. Whether that is acceptable depends on the engine's fog/draw distance, which this note does not know.
- The ROAM figure "<3 % of triangles change per frame" and the brief's "<4 % merges" are not the same statistic (ROAM counts splits plus merges against the whole mesh; the brief's figure is the merge share of events), so they should not be compared directly.

### Gaps
- None of the papers reports pop-size histograms for a *distance-ring* scheme; the only quantitative pop data are ROAM's histogram (error-driven, with queues) and Lindstrom's Table 1 (static error, not temporal change).
- No paper measured the effect of a far fixed-LOD cutoff on perceived popping; ROAM's fog suggestion is qualitative.

## Key question 4: Is "ignore changes below a threshold" (a pixel tolerance of 1-4 px) the standard answer, and what tolerances were used at 640x480-era resolutions vs 1440p?

### Takeaway
Yes: every surveyed method is parameterised by a screen-space tolerance tau in pixels, with 1 px described as "no visible popping" (Lindstrom, Hoppe, de Boer), 1.7-2.1 px as the typical real-time operating point at 640x480-1024x768 (Lindstrom, Hoppe, Ulrich), and 4-8 px as the "cheap" game setting (de Boer); the same world-space ratio projects to about 3x more pixels at 1440p, so a world-space threshold tuned at 480 lines yields 3x the pixel error at 1440 lines.

### Cited Findings
- Lindstrom: results at "1024 x 768 pixels unless otherwise specified"; tau = 1 px gives "virtually no popping"; the 2-minute, 3,230-frame fly-through "was rendered as a wireframe mesh in a 640 x 480 window, with tau = 2 pixels ... a frame rate of at least 20 frames per second was sustained". Fig. 6-7 sweep tau from 0 to 8 px. — [Lindstrom et al. 1996, Sec. 7](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- ROAM: pops measured "in pixels (for a 1000 x 1000 image with 3000 triangles per frame)", histogram 0-10 px, "almost all measure under 1.5 mm on a typical 21 inch workstation monitor". — [Duchaineau et al. 1997, Sec. 8](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Hoppe: "a window of 710x520 pixels ... constant frame rate of 30 frames/sec by regulating the screen-space error tolerance to maintain approximately 12,000 active faces ... Figure 11 shows one frame from the flyover, in which tau equals 2.1 pixels. Over the whole flight, the screen-space tolerance averages 1.7 pixel, and attains a maximum of 3.3 pixels. (Because of approximations in the computation of screen-space errors, the tolerance values are unfortunately not upper bounds on screen-space error.)" — [Hoppe 1998, Sec. 7](https://hhoppe.com/svdlod.pdf)
- de Boer: "When epsilon exceeds a certain threshold tau of, say, 4 pixels, the error will be too noticeable"; demo "tau = 8.0 is used. An average frame-rate of 50 s^-1 is reached with about 11,000 triangles per frame, on a PentiumII 434 Mhz with a Diamond Viper 550" (screen resolution of the demo not stated). — [de Boer 2000, Secs. 2.3, 4](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Ulrich chunked LOD page: "around 2-pixel screen-space error tolerance" with "a 4-meter geometric error tolerance, at 1024x768", about 30 fps on a 1 GHz P3 with GeForce2Go (Puget Sound 16K x 16K dataset). — [tulrich.com chunklod](http://tulrich.com/geekstuff/chunklod.html)
- TUM tutorial: "Subpixel geometric screen-space error: Use screen space error tolerance < 1 pixel" as the alternative to geomorphs for "Avoiding Popping Artifacts". — [TUM terrain tutorial](https://www.cs.cit.tum.de/fileadmin/w00cfj/cg/Research/Tutorials/Terrain.pdf)
- de Boer's T = 2 tau / vres makes the switch distance scale with vertical resolution explicitly ("vres is the vertical screen resolution in pixels"). — [de Boer 2000, Eq. 1c](https://www.flipcode.com/archives/article_geomipmaps.pdf)

### Inferences
- K = H / (2 tan(phi/2)) at a 60 degree vertical FOV: 480 lines -> K ~= 416 px per unit (delta/D); 768 -> 665; 1440 -> 1247. A tile that splits at D = 12.9 s subtends about K / 12.9 ~= 32 px of screen height per tile at 480 lines and ~97 px at 1440 lines (horizontal-view approximation, before any FOV correction for the actual engine). Any world-space criterion (ring or d^2) that looked acceptable at 640x480 therefore shows 3x the pixel displacement per pop at 1440p; to keep the papers' 1-2 px standard the world-space thresholds would need to be tightened by the same 3x (equivalently, the ring radii multiplied by 3).
- The papers' tolerances were set against the *angular* size of a pixel on a 1990s monitor (ROAM states its pops in mm on a 21-inch monitor). A 1440p display viewed at the same distance has pixels about 1/3 the angular size, so "1 px" today is a stricter criterion than "1 px" in 1996; the perceptual target is closer to "1 px at 480 lines" ~= 3 px at 1440 lines.
- "Ignore changes below a threshold" in the papers always means: do not *make* the change unless the projected error exceeds tau — it is a split criterion, not a post-filter on an already-decided split. The papers do not describe suppressing a split that a size-based rule has already requested; the error test *is* the rule.

### Gaps
- No source gives tolerances specifically for 640x480 games of 1996-1998 other than Lindstrom's 2 px fly-through window; de Boer's demo resolution is unstated.
- No source discusses tolerances at 1440p (all are 1996-2005); the 3x scaling is my arithmetic from the K formula.

## Key question 5: Temporal coherence / hysteresis — ROAM's queues, Röttger's blending, Hoppe's geomorphs; what prevents flip-flop at a ring?

### Takeaway
The classic answers are (a) make the decision continuous (Röttger's blend factor b = 2(1 - f), de Boer's trilinear t, Hoppe's timed geomorphs) so a boundary oscillation is invisible, (b) carry state between frames and act only on priority *crossings* (ROAM dual queues with monotonic priorities and a deferral list; Lindstrom's uncertainty intervals; Ulrich reusing last frame's enabled flags), and (c) evaluate the criterion at a predicted future viewpoint (Hoppe); a from-scratch per-frame rebuild with a binary ring test has none of these and will flip-flop on any tile sitting at a ring radius.

### Cited Findings
- ROAM dual queues: "Suppose that every bintree triangle T is given a monotonic priority, meaning a child's priority is not larger than its parent's ... Adding a second priority queue — for mergeable diamonds — allows ... frame-to-frame coherence." Per frame: "Update priorities for all elements of Qs, Qm ... While T is too large or inaccurate: If T is too large or the maximum split priority is greater than the minimum merge priority: identify lowest-priority (T, TB) in Qm, merge ... Otherwise: identify highest-priority T in Qs, force-split T". The loop ends when the max split priority is no longer above the min merge priority (or the triangle budget is hit), "the same priority as if the top-down algorithm had been performed"; a fallback to the top-down algorithm is described when priorities are non-monotonic. — [Duchaineau et al. 1997, Sec. 5](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- ROAM deferral (temporal hysteresis in effect): "The screen-distortion priorities of the triangles change as the viewing position changes, typically in a slow and smooth manner. Recalculating priorities of all triangles for every frame is too costly. Instead, priorities are recomputed only when they potentially affect a split/merge decision. Given a velocity bound on the viewpoint, bounds can be obtained for screen-distortion priorities over time ... the crossover priority (defined as the maximum split-queue priority when the incremental split/merge process is complete) changes slowly from frame to frame (typically around 1% change). Recomputation of a triangle can safely be deferred until its priority bound overlaps the crossover priority. A deferral list is kept for each of the next few dozen frames." Turning deferral off raises priority time from 5 ms to about 43 ms; turning incremental split/merge off raises frame time from 30 ms to 210 ms. — [Duchaineau et al. 1997, Secs. 7.3, 8](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- ROAM also notes "In some cases it is desirable to reduce pops further by vertex morphing" and lists "Vertex morphing is not supported" as a shortcoming of a competing method. — [Duchaineau et al. 1997, Secs. 1-2](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Röttger geomorph: "Since morphing only happens in the leaf nodes of the current triangulation, we can use b = 2 (1 - f) clamped to the range [0, 1] as a blending factor to morph between two levels of detail ... The elevation at these points is interpolated linearly with factor b between the elevation of the lower level (which is the average of the two corresponding corner points) and the elevation of the higher level." Blend factors are stored per node as one byte ("255 morphing steps, which is precise enough in practice"); the shared-edge value is "the minimum of the blending values of the two involved blocks" to avoid cracks; mesh-generation bounding boxes are taken "three times as large, because the blending factors of some blocks can contribute to mesh generation without the blocks being visible themselves." The algorithm is otherwise rebuilt top-down every frame. — [Röttger et al. 1998, Secs. 2.3-2.4](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Hoppe geomorphs: "geomorphs have a lifetime of one second"; vsplit stores "gtime // # of geomorph frames remaining" and a per-frame increment; a refinement "is performed as a geomorph if and only if the region ... [is] visible"; coarsening geomorphs are allowed "one layer at a time" and "require only when the viewer is moving backwards"; "Modified screen-space error metric ... we evaluate the criterion ... gtime frames into the future", i.e. at "the anticipated future viewpoint e + gtime * e_dot depending on whether e_dot . e_hat is negative or positive (viewer moving backwards or forwards)." Refinement work is "amortiz[ed] ... over 3 frames". Fraction of vertices morphing: refinement 28.3 % average, coarsening 2.2 %. — [Hoppe 1998, Secs. 4.2, 7](https://hhoppe.com/svdlod.pdf)
- Lindstrom frame coherence: per block and frame the algorithm computes the uncertainty interval I_u = (delta_l, delta_h] and only re-evaluates Eq. (2) for vertices whose delta lies in the interval that changed since the previous frame (pseudocode lines 11-18: I0 = (delta_l^n, delta_l^(n-1)], I1 = (delta_h^n, delta_h^(n-1)]); "out of the eight million vertices contained in the view frustum, only 14,000 evaluations of Equation 2 need to be made when tau = 1". — [Lindstrom et al. 1996, Secs. 4.2, 5, 7](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- Ulrich 2000: "Update() works from the previous frame's enabled state rather than clearing it ... Per-edge-vertex reference counts track whether a vertex can be disabled." — [Ulrich 2000](https://www.gamedeveloper.com/programming/continuous-lod-terrain-meshing-using-adaptive-quadtrees)
- de Boer trilinear geomipmapping: "t = (d - D_n) / (D_{n+1} - D_n)" is used "as a multiplier for the white vertices of GeoMipMap level 0. This will slowly 'morph' level 0's geometry to level 1's until d has reached D_1 ... replaces the sudden change (popping) of GeoMipMap levels with a smooth transition." — [de Boer 2000, Sec. 3.1](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Distance hysteresis outside the terrain literature (secondhand from search summaries, not read in full): Funkhouser and Séquin 1993 "apply hysteresis by adding a penalty in the benefit heuristics to discourage disturbing visual effects due to fast switching of detail" ([DTIC thesis citing them](https://apps.dtic.mil/sti/pdfs/ADA595276.pdf)); the Blender Game Engine added "a new hysteresis parameter that ... will be added or subtracted to/from the LOD distance to avoid popping when a LOD object moves close to the LOD transition continuously", default 10 % ([BGE commit](https://demo.gitea.com/kannonier8/blender/src/commit/e7d051043dc82c2991eb491e0630d9b1065934c3/release)); Giegl and Wimmer 2007 say late switching and alpha-blending of discrete LODs "either do not work in practice, or defeat the concept of LODs" ([TU Wien preprint](https://www.cg.tuwien.ac.at/research/publications/2007/GIEGL-2007-UNP/GIEGL-2007-UNP-Preprint.pdf)).

### Inferences
- Röttger's b = 2(1 - f) means the morph occupies f in [0.5, 1], i.e. the outer half of each ring (from radius 0.5 R to R, with R = C d max(c d2, 1)): a vertex is fully "in" at half the split radius and fully flattened at the split radius. Flip-flop at the ring boundary is then a change in b of a few/255 per frame, not a topology change, which is why Röttger can afford a stateless per-frame rebuild. This is the cheapest retrofit pattern in the set for an engine that already rebuilds every frame: keep the rebuild, add a per-leaf blend derived from the same f.
- ROAM's protection against flip-flop is structural: a diamond is merged only when its merge priority is below the current crossover and split only when above it, and the crossover moves ~1 % per frame; a tile exactly at a ring radius would alternate every frame in a from-scratch ring test, but in ROAM it needs its priority to cross the crossover again, which it cannot do while the queues are balanced. Translating this to a quadtree means: remember last frame's decision per node and require the ratio D/s to pass the ring with a margin (e.g. split at 12.9, merge at 12.9 x (1 + h)) — the BGE 10 % figure is the only concrete hysteresis width found.
- Hoppe's "evaluate at e + gtime * e_dot" is a look-ahead rather than a hysteresis: for a forward-moving vehicle it starts refinement early (so the morph completes before the detail would have popped) and delays coarsening; it is the only source that ties the window to the geomorph duration (one second at 30-72 fps).
- A stateless per-frame rebuild (the brief's description) cannot implement ROAM-style or Ulrich-style hysteresis without adding a per-node memory of at least one bit (last state) or one byte (blend), which is exactly the one byte per grid point Röttger reports.

### Gaps
- Real-Time Rendering's own passage on LOD hysteresis was not retrieved; the hysteresis-width figures come from a BGE commit message and a thesis citing Funkhouser-Séquin, not from a terrain paper.
- No paper quantifies flip-flop frequency for a stateless ring criterion.

## Key question 6: Vertex / triangle budgets of 1997-2000 implementations, and how the ring factors 12.9 and 18.3 compare to Röttger's C (and c)

### Takeaway
1996-2000 systems ran 1,500-15,000 triangles (or ~15,000 vertices) per frame at 20-50 fps on SGI/early-PC hardware — all comfortably under a 32,767 index budget — and Röttger's published C is 8 (vertex count growing with C^2); the brief's 12.9 and 18.3 are therefore 1.6x and 2.3x Röttger's flat-terrain ring, i.e. about 2.6x and 5.2x his per-frame vertex load for the same tile size, before the roughness branch is considered.

### Cited Findings
- Lindstrom: two-processor 150 MHz SGI Onyx RealityEngine2; 1024x768; at tau = 1 the rendered polygon count is n0/200 with n0 = 13 x 10^6 in frustum (i.e. about 65,000 polygons for that view); 640x480 fly-through at tau = 2 "at least 20 frames per second"; "the number of rendered polygons does not depend on the total number of polygons in the view frustum, but rather on the complexity of the terrain intersected by the view frustum." — [Lindstrom et al. 1996, Sec. 7](https://www.cs.princeton.edu/courses/archive/spr01/cs598b/papers/lindstrom96.pdf)
- ROAM: Indigo2 R10000 Maximum Impact, "3000 triangles rendered the total time per frame is approximately 30 milliseconds. Of this, 5 milliseconds ... view-frustum culling, 5 milliseconds calculating the queue priorities, 5 milliseconds splitting/merging ... and 15 milliseconds outputting the triangle strips"; "On a single R10000 processor Silicon Graphics Onyx with an Infinite Reality graphics board ... 6000 triangles can be rendered at 30 frames per second"; strips average "four to five triangles". — [Duchaineau et al. 1997, Sec. 8](https://classes.cs.uchicago.edu/archive/2004/fall/23700-1/docs/roam.pdf)
- Röttger: SGI Maximum Impact, 250 MHz R4400, "constant frame rate of 25 Hertz"; "C was set to a value of 8, which also proved to be a good choice for other data sets. The value of c was dynamically chosen as to maintain a fixed frame rate of 25 Hertz, which resulted in approximately 1600 triangle fans, or a total of roughly 15000 vertices per frame. This corresponds to a two orders of magnitude reduction of the original 1025 x 1025 height field." Each fan "consists of up to 10 vertices". — [Röttger et al. 1998, Secs. 2.2, 3](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)
- Hoppe: SGI Octane 195 MHz R10K, 710x520, "approximately 12,000 active faces" at 30 fps (Fig. 11: 12,154 faces, 6,096 vertices); the abstract targets "2,000-20,000 triangle faces"; "the VDPM scheme uses 50-75% of the number of active triangles required by bintree schemes for the same screen-space error" (reported from his earlier paper). — [Hoppe 1998, Secs. 1, 7](https://hhoppe.com/svdlod.pdf)
- Pajarola: Indigo2 High Impact R10000, 60 degree view: 86,000 triangles at 20 fps full resolution; 8,000 triangles at 38 fps adaptive; 13 x 13 patches of 4 km x 4 km; scene updates at 1000 m/s used 1,570 ms of CPU over 10 s for 65 patches. — [Pajarola 1998, Tables 2-3](https://www.ifi.uzh.ch/dam/jcr:ffffffff-e53a-93ad-ffff-ffff923549a3/Vis98.pdf)
- de Boer (2000, consumer PC): "An average frame-rate of 50 s^-1 is reached with about 11,000 triangles per frame, on a PentiumII 434 Mhz with a Diamond Viper 550 and 64 MB RAM", tau = 8. — [de Boer 2000, Sec. 4](https://www.flipcode.com/archives/article_geomipmaps.pdf)
- Ulrich 2000: "a few thousand triangles" per frame for the Soul Ride engine's quadtree. — [Ulrich 2000](https://www.gamedeveloper.com/programming/continuous-lod-terrain-meshing-using-adaptive-quadtrees)
- Röttger's C enters the vertex count quadratically: "As C increases, the total number of vertices per frame grows quadratically." — [Röttger et al. 1998, Sec. 2.2](https://otik.zcu.cz/bitstream/11025/15845/1/Slusallek_98.pdf)

### Inferences
- Röttger's flat-terrain test "subdivide if l < C d" is dimensionally identical to the brief's "split when the eye is closer than F x tile size": C <-> F. So the stock always-ring F = 12.9 is Röttger's C = 12.9 (1.6 x his 8) and the steep ring F = 18.3 corresponds to C * c * d2 = 18.3 at whatever slope the engine classes as steep (2.3 x 8). By his quadratic rule the always-ring alone implies about (12.9/8)^2 ~= 2.6x the vertices per frame of his C = 8 configuration at equal tile size and equal view, and the steep ring (18.3/8)^2 ~= 5.2x where it applies. His 15,000 vertices per frame scaled by 2.6 would be ~39,000 — above a 32,767 index cap — but his 1025 x 1025 field and view are not the engine's, so this is an order-of-magnitude indication only.
- Röttger's c (the error-driven knob) has no published numeric value — it was servo-controlled for 25 Hz — so the 18.3 figure cannot be turned into a c. What can be said: his design makes the roughness term dominate wherever c * d2 > 1, i.e. wherever the tile's height error exceeds d / c; the engine's single "steep" class is a two-step approximation of that continuous product.
- 32,767 indices (a 16-bit signed index) sits above every 1996-2000 per-frame budget quoted here (1,500-15,000 triangles / up to ~15,000 vertices), so the cap would only bind under today's 1440p-style tightening (3x ring radii -> up to ~9x tiles for a given terrain), not under the papers' own operating points.

### Gaps
- Röttger gives no number for c and no screen resolution for his 25 Hz figure.
- No source quantifies the per-frame vertex counts of MechWarrior 2 / Interstate '76-class engines; the consumer-PC data point is de Boer's 2000 demo (11,000 triangles at 50 fps on a PII-434 with a 1998-class GPU).
- Luebke et al., "Level of Detail for 3D Graphics" (2002) and Real-Time Rendering's terrain sections were not retrieved; their survey material is not reflected here beyond what vterrain.org and the TUM tutorial repeat.
